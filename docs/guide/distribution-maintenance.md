# Distribution maintainer guide

Internal release operations only. This guide is not exported to `kg-releases`. Public entrypoints are the English and Simplified Chinese READMEs; `INSTALL.md` is the single-language AI guide for versioned private Plugins, customization migration, global guidance and self-check. The product site owns the bilingual user tutorial from service deployment through ChatGPT connection, upgrades and recovery.

## Repository responsibilities

| Private `bYiyLi/kg-os`                                                                         | Public `bYiyLi/kg-releases`                                                                              |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Source, tests, design, CI templates, Plugin, eight current source Skills and unique installer | Only the generated runtime entrypoint, installer, Plugin, eight current source Skills and release CI/CD |
| Private `main` and authorized source `v*` tags                                                 | Generated manifest on `main`, mirrored public `v*` release tags                                          |
| A minimal automatic synchronization workflow                                                   | Full CI, Linux amd64 Docker smoke, GHCR and GitHub Releases                                              |

**Never edit `kg-releases` directly.** Edit `kg-os/distribution/`, `kg-os/plugins/kgos/` or `kg-os/scripts/render-kg-releases.mjs` in the private repository and push to private `main`. **`kg-os/plugins/kgos/INSTALL.md` is the only maintained AI private-Plugin installation guide**; the generator maps it to public `kg-releases/INSTALL.md`. The version catalog lives at `distribution/site/src/content/service-installation/catalog.json`. Every listed stable version has exactly `vX.Y.Z/{zh.md,en.md,INSTALL.md}`: complete bilingual user manuals and an archived AI guide for that same release. These are published snapshots; the editable bilingual release templates remain at the parent directory’s `zh.md` and `en.md`, and `plugins/kgos/INSTALL.md` remains the sole editable AI guide template. Web pages read only the snapshots, while pre-release technical changes are made in the current templates without changing old snapshots or announcing an unpublished version in the catalog. The generator validates and explicitly enumerates the catalog files rather than exporting arbitrary contents of the manual directory. The Agent guide starts from the user's working ChatGPT app and links back to the tutorial when that prerequisite is missing. It does not redeploy the service or duplicate ChatGPT connection steps. Each installation creates a new private Plugin with an explicit official version and, where needed, a revision suffix; user customizations are compared with their old official baseline and migrated after confirmation. Existing app connections are reused, and removal of the old Plugin is a separate user choice after successful acceptance. The private sync workflow exports only allowlisted public files and the eight named Skill directories, with all their references/assets; ontology resources are Markdown navigation, methods and independent adaptations, with upstream originals read remotely at pinned versions; the legacy generic Skill has been removed from private source. Runtime `.app.json` is never exported. It also exports the product licensing documents. All application source, tests and Git history remain private. Public workflows never push back to private KG OS.

The eight-Skill source roster is defined by [D125](../design/decisions.md#d125-unified-eight-skill-plugin) and the [MCP owner](../design/mcp.md#kgos-official-skills). Source synchronization is not a release or a private-installation upgrade. Keep historical tags, archives and versioned manuals unchanged; verify those assets against their own frozen rosters.

## Product website

The V4 product website is developed **only** under private `kg-os/distribution/site/` as an independent Astro static site. The same generator exports its checked source files and pinned `pnpm-lock.yaml` into public `kg-releases/site/`. Locally generated `node_modules/`, `dist/` and `.astro/` are not exported. The website does not use KG OS Kernel/Web/SDK source, private Deploy Keys, credentials, or any API endpoint.

The latest installation routes are `/zh/install/` and `/en/install/`; `/zh/install.md` and `/en/install.md` download that same latest source. Every release has permanent `/zh/install/vX.Y.Z/` and `/en/install/vX.Y.Z/` pages, corresponding `/zh/install/vX.Y.Z.md` and `/en/install/vX.Y.Z.md` downloads, and `/install/vX.Y.Z/INSTALL.md`. Version selectors and language links retain the selected release. Each page binds its guide, AI handoff and official Plugin archive to the same version. The page and download render the exact same archived Markdown body; no separate HTML installation text is maintained. The homepage links directly to the complete user installation tutorial. Compose / Docker and Web / file initialization are supported paths, with Compose + Web recommended. The tutorial continues through HTTPS, creating or reusing the ChatGPT MCP app, OAuth, a real read-only client call, and an AI handoff for a versioned private Plugin. It also covers service upgrades, backups and recovery. AI handles the later Plugin, customization migration, global guidance and self-check using the existing app. Add new site sources to the explicit export allowlist and its tests. Check both the source-site build and a build using only generated public files. Use finished product language in user-facing pages. Record unexecuted Docker, certificate or real-client checks in development evidence, not as a draft banner in the tutorial.

The website displays the **latest verified stable release** from the catalog, with explicit image tags and digest pins. Its Markdown version metadata is independent of the development `package.json` version. The catalog contains only unique canonical stable `vX.Y.Z` tags; `latest` names the highest listed version. Historical guides remain browseable on KGHub, even after latest changes. Do not use an image `:latest` alias or link every historical AI handoff to `main`. The export and standalone website build reject invalid catalog paths, missing or extra snapshot files, and conflicting version metadata/resources. Both languages must use one identical pinned image reference; every concrete official Plugin, Release and fixed-version manual/AI link in the bundle must match its release. Having one correct reference does not permit a second mismatched or unpinned reference. The candidate renderer applies the same bundle validation before writing any generated guide assets.

The generated public `.github/workflows/pages.yml` builds `site/` from a public checkout and deploys `site/dist` to GitHub Pages **independently** of source Validate, Docker CI and Release. Pages is configured to use **GitHub Actions** on `kg-releases` with its own custom domain `kgos.sites.y2l.top` (DNS CNAME to `byiyli.github.io`; configured in the public repository's Pages settings). Astro uses the root base path `/`; the public pages are `https://kgos.sites.y2l.top/en/` and `https://kgos.sites.y2l.top/zh/`. The root chooses a browser-language default, and both languages support light/dark/system themes. No private-source SSH key is available to the Pages workflow. Pushing or generating files alone does not prove that Pages deployment succeeded; verify the Pages workflow, custom domain and HTTPS separately.

## One-time setup

1. Create `bYiyLi/kg-releases` as a **Public** repository with an initialized `main` branch (GitHub's initial README placeholder is sufficient and is replaced at first sync). Change the existing `bYiyLi/kg-os` to **Private**; public forks and previously granted source licenses are not automatically revoked.
2. Create **two separate Ed25519 SSH key pairs**, stored outside either repository:
   - **Public write key:** add the public half in `kg-releases → Settings → Deploy keys`, with **Allow write access enabled**. In the **private `kg-os` repository Actions secrets**, save its private half as `KG_RELEASES_WRITE_KEY`. This key can write only to the public repository.
   - **Private read key:** add the public half in `kg-os → Settings → Deploy keys`, with **Allow write access disabled**. In the **public `kg-releases` repository Actions secrets**, save its private half as `KGOS_SOURCE_DEPLOY_KEY`. This key can read only the private source.
3. Only maintainers may push to `kg-releases/main` or modify its Actions and secrets. Do not grant source access to public contributors, forks or PRs. Public CI accepts generated `main` pushes and owner-only full checks on public main, with no arbitrary source input; Release listens only to generated `v*` tags.
4. Commit and push the private `kg-os` generator, templates and `.github/workflows/sync-kg-releases.yml`. Private `main` pushes generate `source.json` with the exact SHA and automatically synchronize the **allowlisted public files**; `kg-releases` then executes full CI. A private `v*` tag creates a corresponding immutable public tag with the exact source manifest, triggering the public Release workflow.
5. The private `kg-os` repository has **only one GitHub Actions workflow**, `.github/workflows/sync-kg-releases.yml`, to generate and synchronize public content. Its former `ci.yml` and `release.yml` have been disabled and deleted. All source validation, Linux amd64 Docker integration, and formal Release execution belong exclusively to `kg-releases`. Verify both public CI jobs on actual runs; an incomplete/failed public CI is not a completed migration acceptance.
6. Before enabling public binary publishing, resolve KG OS's **AGPL-3.0-only / commercial dual-license obligations**. Simply making the source private does not authorize closed-source distribution of previously AGPL-licensed code. When legally permitted, set the public repository Actions **variable** `KGOS_BINARY_DISTRIBUTION_APPROVED=true`. Until then, source/Docker quality checks may run, but binary candidate upload and Release promotion are blocked.
7. Ensure the `ghcr.io/byiyli/kgos` package grants write access to the public workflow repository and can be anonymously pulled. GHCR may initially create a new package as Private; set package visibility to **Public** in package settings when authorized.

## Candidate CI

The current execution contract is [D123](../design/decisions.md#d123-verified-candidate-promotion) and [Client candidate identity](../design/client.md#verified-release-candidate). Private Actions still only synchronize allowlisted public content. Public CI checks the pinned private main ancestry; external PRs never receive the private read key. Owner-only `workflow_dispatch` on public main with a main-source manifest forces a full candidate run without accepting arbitrary source inputs. A Tag-source manifest requires rerunning the original candidate Run instead. A synchronized release Tag takes the short Tag route and creates no second candidate.

A product candidate runs the unchanged complete Validate and distribution checks, then builds one Linux amd64 image with digest-pinned base images. It exports OCI, checks all content digests and labels, exercises digest-preserving OCI copying, reloads the archive and runs the full isolated Docker smoke. It renders and packages the Plugin and same-version stable manuals from that OCI digest. The license variable must already be true before uploading any binary candidate. Ordinary main does not push GHCR.

The immutable Actions artifact is named `kgos-candidate-<private-sha>-<run-id>-<attempt>` and retained for seven days. CI downloads that exact artifact ID and checks its bytes again before its Run can succeed. Its root contains only `candidate.json`, `image.oci.tar`, Plugin ZIP and stable guide/checksum assets. Logs, coverage reports, caches and source are excluded. GitHub artifact digests are checked strictly. The provenance records source/public commits, Run/attempt, dependency locks, workflow and release-input hashes, tool versions, pinned bases and OCI/config/layer/rootfs/asset identity. See the official [immutable artifact contract](https://github.com/actions/upload-artifact) and [exact artifact ID download](https://github.com/actions/download-artifact).

A website-archive-only source diff runs distribution and source/generated site checks instead of Go/Rust/product construction. The allowlist requires a versioned manual/catalog change and excludes product code, Skills, dependencies, editable templates and workflows. A docs-only commit without a full accepted candidate cannot be tagged for publication; run owner-triggered full candidate CI first when needed. The separate Pages deployment still requires live verification.

Raw command output and third-party test summaries stay in ephemeral runner files. The public report forwards only controlled numeric coverage, stage/exit status, fixed tool names and predefined categories. It never prints arbitrary exception messages, paths, test names or source lines. `unknown` is an evidence limit, not a passing gate.

## Release

1. Obtain authorization for the planned version and set the product/Plugin version. Review tutorial compatibility, then commit and push the private source. Do not update the stable website catalog yet.
2. Wait for the public full candidate CI for that exact private revision. Confirm distribution, complete Validate, OCI roundtrip Smoke, Plugin/manual packaging, immutable upload/download checks and successful Run. Record Run ID/attempt, artifact ID/digest, candidate OCI digest and source revision. A green source check alone is insufficient; expired or absent candidates cannot publish.
3. Create and push the authorized private `vX.Y.Z` Tag pointing at this accepted revision. Sync preserves immutable Tags and produces the public Tag. The new Release workflow does not call CI or rebuild: it locates an accepted candidate, verifies its exact commit, workflow, dependency/tool identity, file bytes and single platform against the Tag, and checks the existing license gate.
4. Release copies the original OCI archive with [preserved digests](https://github.com/podman-container-tools/skopeo/blob/main/docs/skopeo-copy.1.md), verifies the anonymous manifest and actual pull, then stages the exact Plugin/manual bytes in a draft Release. Only after every asset is verified does it publish. Stable assets are the existing Plugin ZIP, three manuals, three-manual checksum file, plus `kgos-provenance-vX.Y.Z.json`; previews retain Plugin plus provenance and are not cataloged. The ZIP's one root INSTALL equals the AI guide byte for byte.
5. Independently verify source Tag ancestry, successful candidate/Release Runs, anonymous image platform/revision/config/digest and all six stable assets. Archive only the verified stable guides on KGHub using the procedure below; production and installed Plugins are separate actions.

### Interrupted publication and rollback

- Discover existing releases through authenticated, paginated release listing, which includes drafts. The by-tag endpoint returns published releases only. Reject multiple releases for the target tag before any publishing action; do not choose or delete one automatically. Reload a created or resumed draft by its exact release ID after asset upload. Read draft assets through their repository-scoped asset ID API; their temporary `untagged-…` browser URLs are not published tag URLs. Published assets retain strict same-tag URL validation.
- Rerunning Release never rebuilds. A complete matching release is reverified using its original provenance and Run attempt, even if the candidate artifact expired. A partial matching release reuses the exact candidate, skips an identical image and uploads only missing assets. Existing asset bytes, classification and provenance must agree; there is no `--clobber` path.
- If a candidate expired before any image or assets were published, rerun the original public candidate CI at its original public commit, verify its new successful attempt and artifact, then retry Release. This is an explicit fresh acceptance, not a hidden Tag-time rebuild. A changed base may produce a new digest.
- If an immutable image Tag or partial release already exists, a newly rebuilt candidate may conflict. Do not replace it. Recover the original candidate from a trusted retained copy and prove all original hashes, or propose a new version. Missing evidence, unknown registry errors and conflicts remain blocked.
- Before activating this redesign, rollback is a normal reviewed revert of its coherent CI/Release/helpers/export changes. Existing Tags retain their historical workflow. Once a new Tag exists, do not move it or mix an old release workflow with a new candidate; recovery must respect that Tag's exact contract. No rollback implies database recovery or production deployment.

### Public repository contribution controls

The source remains private and the generated public repository is maintained only by authorized collaborators and its synchronization identity. Do not remove collaborators or keys blindly. GitHub's [collaborators-only interaction limit](https://docs.github.com/en/communities/moderating-comments-and-conversations/limiting-interactions-in-your-repository) also restricts issues/comments and expires after the selected duration; it is not a permanent PR-only switch. The reported management-interface 403 is an outstanding configuration blocker; this change does not bypass it through another API or browser, alter persistent access, or claim the restriction is already enabled. Preserve the sync identity and obtain the necessary platform authorization before applying and reading back a concrete setting.

### Versioned tutorial assets

Before tagging, maintainers must review the tutorial's technical compatibility with the target release, including configuration, initialization, authentication and upgrade/recovery behavior, and adjust the editable bilingual templates and current AI template when necessary. Never edit an old version directory to prepare a future release. The release renderer cannot infer new product behavior from a version number.

The public candidate job runs the allowlisted renderer after its OCI content and reloaded image have passed smoke verification. Its manifest digest is fixed before GHCR publication; Release must preserve that digest and verify anonymous access before publishing the assets. It reads the parent directory’s editable `zh.md` and `en.md` templates and the same public checkout's root `INSTALL.md` as the current AI template (`--installer INSTALL.md`). Each template declares its own version; the AI template's version comes from its first heading. Templates may advance before a release while `catalog.latest` and all published snapshots remain unchanged. It writes `kgos-install-{zh,en}-vX.Y.Z.md` and `kgos-INSTALL-vX.Y.Z.md` into temporary release output. Controlled substitutions cover applicable version labels, pinned KG OS image references, official Release/Plugin links and fixed KGHub guide/AI URLs. Caddy versions, model examples, historical statements and user-selected upgrade targets remain unchanged. Source snapshots, catalog and the private repository are not rewritten by Release.

The stable Plugin ZIP embeds the generated `kgos-INSTALL-vX.Y.Z.md` as its one root `INSTALL.md`, byte for byte. The bilingual user manuals and the AI guide are separate downloadable assets, and the checksum file covers all three. Read the generated manuals before distribution: replacing a version and digest cannot establish compatibility with changed runtime behavior.

### Archive a verified release on KGHub

1. Independently check the real stable GitHub Release, anonymous GHCR digest/platform/revision, Plugin ZIP and the three guide assets. Download the guide assets into a private temporary directory and verify `kgos-install-vX.Y.Z.sha256`. Check that the ZIP's `INSTALL.md` equals `kgos-INSTALL-vX.Y.Z.md`, its Manifest matches the tag, and all official Skill trees and resources match that release's frozen roster.
2. In the private source, add `distribution/site/src/content/service-installation/vX.Y.Z/`. Copy the verified Chinese asset to `zh.md`, English asset to `en.md`, and AI asset to `INSTALL.md`. Preserve the assets as complete snapshots. Do not regenerate or overwrite existing version directories when preparing a newer release.
3. Review all version bindings: Markdown version metadata and image digest, same-version Release and Plugin archive, bilingual fixed pages/downloads, and `/install/vX.Y.Z/INSTALL.md`. Add the stable tag to `catalog.json`; set `latest` to the highest verified stable tag. The catalog is the finite page/export list, not a free-form path configuration.
4. Run distribution tests, source-site and generated-public-site checks/builds, link/format checks and browser validation. Confirm both the new version and an older retained fixture, version/language switching, raw downloads and AI handoff resources. Only then commit/push through the normal separately authorized sync and Pages process. Verify live fixed/latest pages, selected-version persistence and downloads after Pages succeeds.

For the first `v0.3.0` backfill, the newly authored KGHub snapshots are checked against that actual release and verified Plugin asset; they do not claim to be original release assets. Its original Tag and ZIP contain the earlier installer and remain unchanged. Until a later release uses the new packaging workflow, use KGHub's fixed-version AI guide for the current Plugin installation interaction, and the actual old ZIP as the `v0.3.0` technical/Skill baseline. Never rewrite old Tags, mutate an old ZIP or claim absent release assets were published.

The resulting GitHub Release public tag points to a commit in this distribution repository; private source identity is recorded by full SHA in the release notes and image label.

## Security

- Public-write and private-read credentials use **distinct repository-scoped deploy keys**. Never reuse either key for another repository.
- Never include private application source in this repository, a public artifact, test reports, Actions cache, logs or Release assets. Only explicitly allowlisted public tooling is exported.
- Run only source commits in private `main`; public PRs and arbitrary workflow dispatches must never receive a private deploy key.
- Workflows, read-only checkout rules and public content are developed exclusively under private `kg-os/distribution/`.
- Treat publishing, production deployment and tagging as separate operations.
