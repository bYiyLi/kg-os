## 10:09 — 澄清结构化、全文与向量联合检索的现有能力

Scope and authorization: 用户要求将本轮联合检索的澄清记录到 vlog，然后继续逐项讨论。本次只新增日志，保留现有未提交改动；不修改设计真源、KG OS 或 Lithograph 代码，不提交、不推送。

### 澄清结论

- “结构化检索和向量检索不能一起使用”不是当前能力缺失。撤回此前把托管向量接口的结果数量限制概括成“Lithograph 必须新增联合检索能力”的判断；不据此要求重新设计 KG OS。
- Neo4j 的 Cypher 25 支持 `SEARCH ... VECTOR INDEX ... FOR ... WHERE ... LIMIT ...`。Lithograph 的 Raw Vector 路径已有对应实现：传入查询向量，在 `SEARCH` 内按索引声明的附加属性过滤，再取近邻结果。这里是属性条件过滤，不代表任意图遍历条件都会自动进入向量索引过滤。
- 全文检索可通过 `db.index.fulltext.queryNodes()` 取得匹配结果，再接 `WHERE`、`ORDER BY score DESC` 和外层 `LIMIT`。省略 procedure 内部的 `limit`，可以避免在结构化过滤之前先截断结果。接口没有任意结构化过滤参数，不等于不能与结构化查询组合。
- 托管向量的 `db.index.semantic.queryNodes()` 也能接外层 `WHERE` 和 `LIMIT`；当前差别是内部 `limit` 必填。先取 N 条再过滤，可能漏掉 N 条之外仍符合条件的数据，不能据此保证得到过滤范围内最相似的指定数量结果。
- 因此，需跟进的是托管向量结果数量限制的具体处理，不是重新设计一套联合检索能力。[Graph 当前合同](../design/graph.md#graph-公共调用合同)中关于返回候选之后再过滤的限制仍然成立。

### 尚未采纳的方案

“允许托管向量接口省略内部 `limit`，把结构化过滤、排序和最终数量限制放在外层”是本轮提出的一种方案，尚未确认为接口变更，也没有实现。该方案可能需要处理索引中的全部向量，不能把结果语义可表达等同于具有索引内过滤的执行效率；本次不冻结无限制检索或全量扫描的默认行为。

### 核对依据与验证

- [Neo4j Cypher 25 SEARCH](https://neo4j.com/docs/cypher-manual/25/clauses/search/)：向量查询语法与索引内属性过滤。
- [Neo4j Full-text procedures](https://neo4j.com/docs/operations-manual/current/procedures/built-in-procedures/#procedure_db_index_fulltext_querynodes)：全文 options 支持可选的 `skip`、`limit` 与 `analyzer`。
- 本地 Lithograph 核对位置：`/Users/yi/Code/Lithograph/docs/design/vector.md` 的“两套并列能力”“文本查询 surface”，以及 `docs/design/full-text.md` 的“Query-time analyzer 与结果语义”；options 实现在 `crates/lithograph-core/src/query/completeness/execute/registry.rs`。
- 本轮前序讨论已实际运行 `cargo test --locked -p lithograph-core --test phase08_search_ingestion vector_index_searches_nodes_with_score_and_filter -- --exact`，结果为 1 passed、0 failed；只证明该 Raw Vector 属性过滤测试通过，不代表托管向量已支持省略 `limit`，也不是新运行的 Neo4j 对照测试。

### 决定与文档整理

1. 撤回将 YAML 正常解析判为设计缺陷的结论。示例中按 YAML 语法去掉格式缩进是预期行为，不能仅比较 YAML 源文本的空格数与解析值，就声称正文丢失。先前用手写拼接构造的失败例子，只证明那种拼接方式不能保持预设的原始字符串，不能证明 KG OS 的标准 YAML 合同或尚未实现的 renderer 存在缺陷。
