# 起始状态与知识世界定位

用于创建或选择 Branch，以及保持世界用途的连续性。名称、目的、源 State 和实际内容各是不同依据；不要用名称代替内容验证。

## 从实际目录和用途定位

使用实际可访问 Instance 的 Branch 列表/概览、准确Head、已有简介和相关模型/数据来判断候选。已给明确目标不重复全库搜寻；未知连接不臆造全账户目录。名称相同但属于不同Instance时是不同引用；名称被删除后重用，也不能只靠名称证明仍是原来的世界。

名称优先表达可区分用途，实验名可表明与某世界的关系，但不要强制前缀、大小写转换、编号或斜杠树。名字中的层级不建立数据库父子关系；共享祖先也不建立“父分支更新自动下传”的订阅。保留实际名称，按当前合同验证合法性。

目标同名已存在时先核对是否正是要继续的世界；可能复用则复用，不自动删除重建、移动Head或悄悄换随机名称。无法裁决的身份/用途差异只阻塞相关操作。创建超时或报已存在时，同名可能由自己或其它调用建立，先核实实际State和内容，不把存在等同于本次成功。

## 三种不同起点

| 目标 | 对源 State 的要求 |
| --- | --- |
| 不继承其它业务模型/数据的全新世界 | 找到仍可访问、KG OS-valid且确实不含不需要业务内容的基线；“有效”不等于“空” |
| 复用既定公共模型或资料的独立领域世界 | 核对将继承的全部类型/数据范围符合任务；不要声称只复制其中一个Domain |
| 对已有世界试验另一演进方向 | 使用该世界实际选定的State，保留原有完整模型和数据，源分支后续前进不改变已选基线 |

普通 `branch.create` 只建立指向源State的引用，不创建新Commit、不自动初始化领域模型，也不复制配置、认证或Provider进程。创建前按实际连接手册解析并固定要使用的源State；相应名称字段与StateRef格式不要混用。调用后确认新名称指向实际返回State，源引用未被本操作移动。

所谓干净基线不是裸Lithograph Root；后者可能尚无KG OS内部结构，不能作为高层有效源。可核实的初始KG OS bootstrap State可能适合，但不能假定每个库都保留它、它永远可达，或凭“最早Commit”就认定干净。业务模型为空也不证明不存在Graph写入的用户知识。声明没有继承业务内容需要相应覆盖证据，不能用一页目录或一条Label零计数代表全库。

找不到符合要求的基线时，不默默从当前main继承后称新空库，不删除main内容“腾空”，也不凭空发送 `empty:true` 等参数。提出当前可行的有界方案：寻找已知有效基线，或在另获相应授权的范围准备有效空快照/迁移/独立Instance；不能把方案写成已经完成。

## 当前快照与祖先历史

在新分支清除继承的业务对象，即使获得授权且当前快照为空，也不会擦除来源祖先中的模型/数据。要求历史不含某类资料或真正权限隔离时，这种清空不能满足；不要把“当前干净”宣传成“历史完全独立”。分支内的Graph/Snapshot边界不承诺安全擦除。

## 用途说明而非新元数据系统

现行Branch只有名称和Head。已有Commit Message中的简介可帮助定位当前State，但多个Branch可共享它，快进可换成另一份简介；不能作为永久绑定Branch的身份。无规范简介时如实说明，不根据名字伪造已保存Description。

不发明 Branch Description/Type/Owner 字段，也不把State Data当替代品。State Data属于Commit，几个Branch共享该Commit时，通过其中一个Branch修改Data会被其它引用读到。需要保留历史、进入查询/约束/合并的用途事实，须由实际模型任务处理，不能自设sidecar业务真源。这里只判断已存在的证据，不强制用户为每个Branch存一套管理对象。
