# 知识世界的边界

“知识世界”表示用户希望独立理解和持续演进的一组模型、知识与语境，不是 Kernel 新对象。用途可以由明确任务及现有材料确定，不要求新建 World 节点、注册表、评分或固定字段。

## 选择哪种边界

| 真实需要 | 判断 |
| --- | --- |
| 只是增加主题，仍共享对象身份、模型和日常关联 | 优先沿用当前 Branch；需要模型组织时由 Ontology 处理 Domain，不为分类建分支 |
| 希望小说经验、学习等领域各自长期积累、独立改模型和数据 | 可以建立长期 Branch；没有未来合并计划也完全成立 |
| 同一世界需要试验另一模型/方案而不推进既有 Head | 从该世界明确 State 派生实验 Branch，保留完整起始语境 |
| 只需查看过去状态或固定一个已存在版本 | 直接读取真实 Commit；需要人类可识别的引用且获准时可用 Tag，不默认新建 Branch |
| 需要独立认证、文件、运行配置或其它真实物理隔离 | Branch 不提供这些保证；提出 Instance 层方案及实际边界，不顺带部署或修改权限 |
| 只是多个来源意见不同、任务变多或 Agent 变多 | 本身不构成必须分支的理由；现有模型能容纳不同主张时在同一世界表达 |

不同主题可以属于一个世界，同一主题也可以有多个合法知识世界。既有分支能满足新的用途、身份和演进要求时复用；它的名字相似不证明用途相同。明确希望独立维护时，不以“减少分支数”作为否决理由。没有通用分支数量阈值或必须的分层目录。

## 分开后的代价也要明确

两个 Branch 各自可有模型和内容，但普通关系边仍属于选定的单个 Snapshot，不会因为两个世界都出现某个Ref就形成跨分支实时关系。它们不自动同步、合并或共享后续改动。频繁需要同一组实体的直接关联与统一修改，通常支持放在同一世界；偶尔参考另一世界不要求为此整体合并。

不同 Branch 可能继承相同元素身份与共同祖先；不能把它们一概当互不相关副本，也不能因此认为它们永远语义一致。分别创建的同名对象未必同一身份。未来融合时重新核对模型及实例含义，不靠世界名称匹配。

安全边界与语义边界分开。同一数据库里的“private”名称、Domain、不同Head或隐藏在导航之外，都不是权限隔离。独立 Instance 也须实际配置和验证访问控制，不因有两个文件就承诺隔离已完成。本规范仅决定所需边界，不提供部署/备份合同。

## 长期与派生用途

长期世界可持续多年，低频更新不代表废弃。实验世界可被长期保留，长期世界也可后来融合；不要凭前缀强制生命周期。`main` 是实际默认引用，不自动等于全部领域的主库、唯一可信内容或所有实验的合并目标；保留它当前的系统职责，不因这个使用原则擅自删除或改默认配置。

系统 `vlog` 是普通长期 Branch 的一种约定用途，不是日志权限特区。记录什么、如何建模、是否需要保留某条运行证据属于 VLog/知识工作；分支存在不证明记录规范、维护任务或调度已建立。日常维护安排也不由本规范接管。
