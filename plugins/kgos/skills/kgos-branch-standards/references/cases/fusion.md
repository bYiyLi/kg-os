# 决策案例：阅读、选择性引入与融合

应用 [融合与生命周期](../integration-and-recovery.md)。本例讨论完整State的操作边界，不定义业务模型、具体迁移规则或新的SDK。

## F1：学习库参考写作经验，不一定要合并

用户只希望回答问题时参考小说经验库，分别只读即可。用户要把三条写作方法纳入已有学习模型，则限定引入这些内容及实际必要关联，按目标身份与语义处理；不把整个小说世界Merge进去，也不声称自动保留来源完整历史。

相邻情况：用户明确要融合两套完整知识世界，相关模型与实例已检查兼容且授权覆盖，则可以整体Merge。若还要求两个原世界不变，可在合适目标State建立综合Branch再合并；用户已指定直接推进学习Branch时，不为模板而强制第三个分支。

## F2：整体Merge会带来删除，不只是新增集合

共同祖先S有对象A和B。小说分支从S删除A保留B；学习分支从S保留A/B并新增C。二者没有对A的相反修改时，三方Merge可能把来源的删除带到目标，得到B/C而不是A/B/C。

因此从同一个混合库分叉、分别删掉“不属于自己的部分”后再融合，不能按两边当前内容作简单并集理解。必须核对具体祖先变化及目标保留需求；用户只要求加入B相关内容时，选择性迁移比全世界Merge更符合授权。

## F3：技术无冲突不等于同义模型或正确事实

两个世界都叫Character，但一个表示小说人物，另一个表示字符；或者两个独立节点有同一业务身份。底层可能出现冲突，也可能接受并存；不能以无冲突推出语义一致，更不能自动改名、合并实体或删一份。

Branch任务识别融合风险和未决项；具体模型适配与事实身份遵循对应职责。已有明确模型映射和用户决定时可以继续，不要求形式化“全库语义证明”。只处理受到本次融合影响的边界，不将局部合并变成无界审计。

## F4：只读比较不能偷偷建立Session

用户说“先看看两个世界差在哪，别修改”。读取固定State的Diff、模型和相关实例；不能以 `merge.start` 不移动Head为理由启动它，因为Session本身是持久化操作状态。

用户已授权完整合并时，必要Session步骤属于实施范围。ready、fast_forward、up_to_date描述候选状态，不等于finalize已执行；特别是fast-forward可能只移动引用，不产生新Commit或采用新的Message。

## F5：来源与目标变化的影响不同

Session固定source=S1、target=T1。来源后来到S2不会自动扩大本次合并，仍处理S1；用户要求含S2时须重评范围。目标后来到T2则不能在旧target基础强行finalize，不能通过换revision或reset目标伪造安全。

回执丢失时检查目标Head、历史及对应Session；目标刚好等于S1可证明当前状态，未必证明哪次调用完成。丢失Session token时仅查当前实际列表识别属于本任务的工作，不能清理全部未完成Session。
