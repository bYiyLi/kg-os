# 决策案例：继承与基线

应用 [起点与世界定位](../origins-and-identity.md)。S0/S1等只是本例的已观察状态代号，实际调用须使用真实StateRef，不能把代号当Commit ID。

## O1：从main创建，并不会筛出小说数据

已核实main的S1包含学习与小说模型/数据。用户要求全新小说经验世界、不继承学习内容。直接从S1创建novel-writing会获得完整S1，不满足“新空世界”；按Domain命名也不会自动筛选。

若实际可读取的S0已验证为KG OS-valid且无业务模型/用户知识，可以从S0开始。S0可能是bootstrap完成后的状态，不是裸Lithograph Root。找不到这种基线则说明缺口，不擅自清空main或伪造 `empty` 参数。

相邻合法情况：用户要对整个现有S1做实验，继承全部内容正是正确行为，无需先清理、复制或初始化领域模型。验证创建结果等于所选源State，源Head不被创建操作移动。

## O2：有效不等于空，当前空不等于历史空

`evolution.get` 返回consistency valid，只证明高层一致性；概览没有Definition，也不能排除通过Graph写入的业务对象。不能以二者之一替代覆盖相应数据的空基线证据。

如果在新Branch删除了所有旧业务数据，当前快照可能满足空内容要求，但其祖先仍保留旧内容。用户要求历史不含私密资料时，这不是合格方案。只要求实验初始可见内容为空且明确授权清理时，可评估该方式的真实影响，不把它永久禁止，也不声称其擦除历史。

## O3：分支隔离不覆盖共享State Data

novel-writing与experiment刚创建，均指向同一S1。通过experiment设置State Data中的说明，novel-writing读取S1也能看到该注释；没有创建新Snapshot。这不能作为experiment独有Description。

如果任务明确要求一个独有状态上的可变诊断注释，可在授权范围创建对应新State后处理；但不应为了每个Branch的用途说明强制额外Commit。需要历史化的业务事实应按真实模型处理，不把sidecar当知识真源。

## O4：同名世界与不明回执

请求创建novel-writing超时，随后发现同名Branch已在所期望S0。核对实际目标及任务条件，可报告目标引用现已存在；不能仅凭同名归因本次调用，也不删除重建或改名novel-writing-2再试。

若该Branch已前进到含其它资料的S2，先检查它是否同一任务的后续工作或其它人的世界，不能把它强移回S0。用户明确要继续既有小说库时，复用正确世界；用户确实需要另一个独立方向时，再选不冲突且意义明确的新名称。
