# 实例身份、复用与关系

使用已有 Ontology 的实例粒度、身份范围和关系语义；本规范不重新定义实体或关系类型。定位已有知识可以读取相关模型、按业务条件查询候选及回读实际 Ref，不因此开展全库巡检或一般检索研究。

## 新增、复用还是待确认

| 证据情况 | 处理判断 |
| --- | --- |
| 同一身份作用域内，既定稳定键与可信输入一致，且无身份冲突证据 | 复用对应实际实例；仅更新本任务有依据的值 |
| 名称不同，但有明确且相容的别名/改名依据或同一稳定身份 | 不重复创建；按既有字段及授权更新显示信息 |
| 名称相同，但确认属于不同身份/作用域 | 保持不同实例；同名不是去重条件 |
| 只有相似名称、语义检索分数、共同上下文或不完整键 | 仅作为候选，核对决定性身份信息；不足则不强行归属 |
| 查询失败、权限受限、只看一页或 top-k 未命中 | 不能据此证明对象不存在；补足适用查询，或报告未确认 |
| 同一已确认键命中多个对象，或键与其它可靠身份信息矛盾 | 先定位数据冲突/键作用域，不自动任选一个、改键或合并全部 |

业务键的作用域可能包含组织、来源、租户或项目。不要把 `n:...`、`r:...` 当跨库身份；实际实例须连同所属知识库和 State 理解。显示名称、数据库 element identity、业务唯一键分别使用，不把旧 State 的 Ref 当现态必然存在。

身份不确定时，可以按**已存在且允许未决记录**的模型保存原始陈述而不连接到猜测实体；没有这种表达时，保留拟处理信息并说明该项未写入，不临时新建 PendingEntity/Claim 类型。仅保存不依赖身份的独立部分时，不声称原任务的全部关联已经完成。

去重判断还要看模型的实例粒度。同一个人、同一来源、同样文字可能对应两次观察或两段任职；不能因值相同删除合法的不同事件。发现旧重复记录不等于获准合并/删除/重接所有边；当前创建任务先避免新增重复，系统性清理留在相应授权范围。

## 关系的事实与归属

创建或更改关系前核对已有关系类型的含义、正确端点身份、方向，以及关系属性属于谁。人员本人属性不能从任职关系随便继承；某项目实施某决策的证据不能套到所有应用该决策的项目。按模型读取允许的角色和有效期，而非自造命名规则。

资料同时提到两对象，不证明它们有依赖、因果、隶属或等价关系。原文提到“考虑合作”也不证明正在合作；模型若只表达已发生关系，就不能为保存意向擅自建立确定关系。已有模型允许以明确状态表达候选关系时，才按那个合同保留意向，不能默认所有关系都有这样的状态。

同类型、同端点并不天然唯一，可能角色、期间、证据归属或事件身份不同。查找已存在的同一事实时使用模型规定的判等条件；若现有值完全一致且无新增证据，不再重复写入。索引相似度和数据库约束无法替代事实判定。

纠正错连的关系前确认新的端点和变更依据。不同业务事件不是对旧关系的简单换端点；关系实体可能被底层替换，核实实际返回的 Ref/transition 及新 State，不假定原 `r:` 永远不变。修改授权不默认涵盖相似名字的其它关系。

## 保持无关知识

新资料提供一个字段，不等于提交完整对象替换。保留未涉及的属性、Label 和关系；字段缺失、未观察到某条关系和明确请求撤销该关系是三种不同输入。只有原范围内明确的删除/清空授权和事实依据才能改变相应旧值，不能通过“清理多余字段”改变用户模型或其它对象。
