# 决策案例：实体与关系

先应用 [身份与关系](../identity-relations.md)。案例模型和所有记录均为给定合成条件，不是本体推荐模板。重点是同样的名字或端点，为什么会导致不同的实例处理决定。

## I1：名称不是身份，已确认身份也不需要重复新增

既定 Person 模型使用 `(directory, personKey)` 联合键；`name` 和可选 `email` 均为 STRING。当前已验证的目录 A 中有 P1、P2 两人，都叫 Alex，P1 邮箱为 `a1@example.invalid`。用户明确授权按目录 A 的正式更名记录将 P1 的显示名改为 Alicia，更名材料未提邮箱。

**决定**：准确定位 A/P1，更新 name，保留原邮箱；P2 不受影响。不是对 Definition 的 Property 改名，不使用 `renameFrom`，也不创建新的 Person。

### 预期实例 P1

```json
{
  "labels": ["Person"],
  "properties": {
    "directory": "A",
    "personKey": "P1",
    "name": "Alicia",
    "email": "a1@example.invalid"
  }
}
```

**危险反例**：批量更新所有叫 Alex 的人；因为名字变了新建 Alicia；材料未写邮箱便删除原邮箱；把目录 B/P1 也改掉。

**相邻合法情况**：材料只说“Alex 更名”，没有目录键且存在两候选时不能选第一个；需要定位信息。用户后来确认是 A/P2，则只修改 P2。确认是此前不存在的第三人且其既定身份完整时，可新增；“名称不唯一”不能被误读成永远不得新建。

**验证**：A/P1 的实际 Ref 连续、name 更新且邮箱未丢；A/P2和B/P1不变；对应 Person Definition 未改变。按业务键定位真实 Ref，不把 JSON 里的 P1 当 `n:` 元素 ID。

## I2：共同出现不构成关系

已有 Company 和 `Person -[WORKS_AT {role, periodKey}]-> Company`。periodKey 表示任职事件，role 属于本次任职。输入“Alex 与公司 O 出现在同一份活动名单”不支持任职关系；即使 Person 身份已确定也不建立 WORKS_AT。

改为“正式目录记录 A/P1 在 O 担任 reviewer，任职事件 M1”，且参与对象和授权都确认后，可按给定关系语义保存。role不能借用A/P1其它工作的 engineer；不能反向连接成 Company→Person。若对象身份尚不明确，关系写入也保持未决，不能为了关系先造一个猜测 Person。

**验证**：关系类型、实际起终点、role、periodKey都对应明确依据；不新增反向同义边，不改变人的其它任职。没有关系写入时报告“依据不足，未创建”，不是“已确认此人未在 O 工作”。

## I3：相同端点可能是不同事件

A/P1 与 O 已有事件 M1 的任职关系。再次导入同一 M1且角色/依据没有新信息时，复用或无需写入。明确提供新的任职事件 M2，即使人、公司和角色相同，也不是重复；按已有模型新增 M2，保留 M1。

若仅提供“仍在 O 任职”，没有支持新事件的依据，不凭导入时间创造 M2。若一条 M1 错连到了 A/P2，用户有依据授权纠正端点，则修正这条关系；按实际返回处理可能的关系 Ref 替换，不连带合并 P1/P2。

## I4：查不到不等于没有，冲突键也不能绕过

只看语义检索前五项没有匹配，不足以证明新人物不存在；应用既定键或可靠识别条件继续有界查找。失败/无权限时明确不能确认。

同一已确认业务键命中两个实例，应报告局部身份冲突；不能随意挑一个、改个键创建第三个，或在当前保存任务里全库合并。已有可靠唯一约束且完整精确查询确无记录时，可以正常创建，不要求为了证明不存在扫描所有无关对象。
