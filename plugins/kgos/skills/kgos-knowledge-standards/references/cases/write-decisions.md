# 决策案例：写入边界与恢复

先应用 [写入与核实](../write-verification.md)。这些情境给出客户端所知事实，教的是知识结果的正确判断；不是要求制造网络故障、创建测试分支或执行固定脚本。案例不会赋予对用户库的操作权限。

## W1：表达不完整时不改模型，也不伪造完整性

用户要求保存一项尚未验证的性能猜测。现有目标字段语义只能容纳“已测得的性能提升百分比”，没有其它可用表达。不能填预计数值当成实测值、临时加 certainty 字段或降低约束；指出“猜测不能忠实表示为已测得结果”，该部分暂不写。

**相邻合法情况**：已有 Note.text允许带条件的陈述，则可完整记录猜测和未测试状态，不必强行新增证据/假设类型。用户另有模型设计修改授权时，宿主先按模型职责处理后再保存，不把本 Skill 的限域变成对整个任务的永久禁止。

缺少一个可选来源字段不是普遍阻塞；只要现有表达能保留必要归属就可写。相反，普通资料整理请求不授权顺带保存其中的凭证，即使字段类型接受也不自动写入；明确的专门保存请求另按宿主安全规则和目标权限处理。

## W2：独立批次与不可分事实

用户要求保存三条相互独立笔记，允许逐条完成，其中一条身份无法确认。可以保存其余两条并明确第三条未写入；不能以两条成功报告三条全部完成。

若用户要求“这次导入全部成功才写入”，不能擅自采用上述部分完成。一个人、某任职事件及其关联共同构成同一事实时，也不能只创建半条关联后宣称完成；采用实际支持原子性的操作，或说明真实限制，不把一个 JS 脚本当全批次事务。

## W3：回执丢失后先观察，不先创造新身份

已授权向 Branch `review` 保存 Note I1，key 是本任务已确认的来源记录标识。提交后超时，不知道结果。后续在同一知识库的 `review` 新 Head 按 key 读到且核实了完整目标内容：I1只有一条，text/status/basis都符合本次意图。

**决定**：目标已存在，无需再次创建；报告“已核实目标状态”，不能仅由此认定是本次超时调用创建的，也不能改用I2重试。若旧结果与目标不同，需要比较新变化和证据，而不是把它当未保存。

### 核对目标 I1

```json
{
  "labels": ["Note"],
  "properties": {
    "key": "I1",
    "text": "保留原始陈述。",
    "status": "reported",
    "basis": "来源记录 I1"
  }
}
```

**相邻合法情况**：明确原子请求被服务端拒绝，且最新读取确认未创建并仍满足原授权，可修正后提交；当前仍不可读取时，结果保持未知，不能声称未写或不断换身份再试。查询范围不完整也不能据“没看到I1”认定未创建。

**验证**：目标 Branch存在一条语义与身份都符合的I1、无重复；其它分支不因恢复被移动。用模拟“忽略返回值再回读”的测试只证明状态核对路径，不证明真实网络超时已被测过。

## W4：基线变了，不能只替换 State 字符串

原先读取 P1后准备改name；另一个任务更新了email，原Patch收到 `STALE_BASE_STATE`。重新读取目标分支最新State及P1，保留新email，只提交仍然被授权的name变化。

**危险反例**：把旧完整目标对象配上新baseState重发，导致并发email被覆盖；或者为了“解决冲突”reset整个分支。

**相邻合法情况**：另一人也改了name，而且与本次来源不同，就先核对变化含义及证据，不能沿用“不同字段可继续”的结论。采用Graph写入时也不能发明baseState参数来声称同样保护，须使用其真实合同支持的一致性方式。

## W5：关系被替换或后续读取失败

授权纠正一条错连的关系，实际返回旧Ref到新Ref的transition；回读新的关系Ref及端点，确认角色/属性未丢失。不能继续以旧Ref已不存在断言“保存失败”并重建另一条关系。

写入回执已明确成功，之后读取失败，只能说“写入已返回成功，回读未完成”，不把整次写入说成已回滚。多个独立调用只完成前一项时，按实际结果报告部分完成，不自动逆转其它任务的成功写入。
