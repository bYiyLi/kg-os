# 决策案例：新旧知识的不同关系

先应用 [更新与冲突](../updates-conflicts.md)。以下几个分支分别给出条件，不是对同一库依次执行的连续流程。编号和资料均为合成输入；只处理既有模型和实例，不重新设计历史/论断结构。

## U1：现实变化，还是此前记录错误？

给定 Device 模型：key 为唯一必填 STRING；currentVersion 是当前已确认运行版本；notes 为不受本次变更影响的可选 STRING。A1 当前值为 `1.0`，notes 为“保留人工备注”。用户任务只需维护当前值，不要求另存业务有效期间。

**变化分支**：运行记录 R2 明确证明 A1 从原来的1.0升级到2.0，用户授权更新。将 currentVersion 更新为2.0，保留备注。数据库旧 State 可查看原来保存的1.0，但不是凭 Commit 时间推断升级时刻。

### 预期实例 A1

```json
{
  "labels": ["Device"],
  "properties": {
    "key": "A1",
    "currentVersion": "2.0",
    "notes": "保留人工备注"
  }
}
```

**纠错分支**：原始登记材料证明旧值1.0是抄写错误，A1从未运行过1.0，实际是2.0。当前值也应改成2.0，但处理理由是纠错；不能编造“从1.0升级到2.0”的业务事件或有效期。本例没有独立证据字段且 notes 明确不受本次变更影响，因此在任务结果说明 当前输入中实际提供的依据，不向 notes 追加纠错日志或偷偷新增字段。其它模型有已授权的证据位置时才使用该位置；历史库版本仍含旧错误，并不使错误成为曾经成立的事实。

**危险反例**：两种输入一律新增一次“升级事件”；或者因更新都得到2.0就丢掉为何修改的区别。

**相邻合法情况**：任务另要求业务历史，且已经存在带有效期的 Deployment 实例模型，就据实际起止证据更新它；若模型尚不能表达则指出缺口，不在本 Skill 里加字段或类型。当前模型只需当前值时，也不能无理由阻止上述合法更新。

**验证**：A1 当前值与依据一致，notes及其它设备不变；报告能区分变化与纠错。底层历史回读只能证明以前存过什么，不能独立证明升级事实。

## U2：补充不是对象替换

已有资料记录的作者、来源和标题都已核实。新材料只给出更正后的标题，用户授权改标题；保留未涉及的作者与来源。新材料中的空白作者栏不是撤销旧作者的指令。

相邻条件：用户明确确认旧作者归属错误并授权清空，模型允许作者缺省，才清空该值；不能把“保留未提字段”解释成禁止已明确授权的纠错。若模型不允许缺失，不伪造 unknown 字符串通过约束，也不擅自改成可选字段。

## U3：条件不同，不是证据互相否定

记录 A：“组件 C 在测试环境 T 的2.0版本支持功能 X。”输入 B：“组件 C 在生产环境 P 的1.0版本不支持 X。”主体相近但环境/版本不同，按现有模型分别保留；不能让后到的 B 覆盖所有 C 的能力。

若输入 B 明确指向相同环境 T、相同2.0和同一验证时间，却给出相反结果，才进一步核对是否同一命题、材料是否独立和是否有可裁决证据。来源较新、篇数更多、措辞更肯定都不自动足以裁决。

## U4：保存冲突，不把两种说法同时当事实

给定模型已经有 `Report {reportKey, subject, text, basis, assessedAt}`，其含义是“某来源在该时点评估的说法”，不是已证实事实。两个报告对同一环境、版本和时点结论不同，可以分别保留出处完整的 Report，并在任务结果说明冲突尚未解决。

若当前模型只有一个“已证实值”字段，不能随意填一个、把两个互斥值拼成无归属正文或自动创建 Report 类型；说明该写入的证据/表达缺口。若有原始可复现实测确认一方抄错，则按授权修正错误，不把纠错拖成永久未决。

## U5：来源撤回，不等于主张已被证伪

支持某结论的材料被撤回，先核对撤回范围/原因及其它依据。撤回仅因版式或版权，不等于实验结果为假；撤回明确指出关键数据伪造则会实质削弱相关结论的依据。

按现有模型更新证据可用性或认识状态，并保留归属。没有足够证据证明相反命题时，不直接把 true 改 false；不得删掉唯一来源后仍无说明保留“已证实”状态。仅链接暂不可访问时，报告访问受限，不推断材料已撤回。
