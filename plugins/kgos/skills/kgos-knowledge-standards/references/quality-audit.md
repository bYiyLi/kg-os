# 知识质量审计与使用验收

<!-- cspell:words SHACL -->

本参考有两条加载路径：`SKILL.md` 第 3 节的复杂内容或独立结果 Review，只读取本条适用的[内容 Review 合同](#内容-review-合同)和必要的[外部方法适配](#内容质量的外部依据与适配)；第 4 节的独立质量审计或深入使用验收，才按实际范围使用完整审计方法。普通内容 Review 不触发第 1、3、5 节的全量盘点、覆盖统计或审计报告要求，也不自动扩大为全库审计。

本参考提供取证与 Review 判据，不是额外 Skill、模型、评分服务或数据迁移授权；读取不新增查询、写入或扩展范围的权限，具体模型与查询接口仍以目标实例的 `kgos_docs` 为准。

## 1. 确定范围和证据边界

1. 明确获准 Instance、Branch、Domain/Definition、业务实体与问题；Domain 组织模型，不自动分隔数据。每个目标 Branch 固定自己的不可变 State。跨 State 比较分别说明版本、业务时间和覆盖，不合并计数。
2. 按实际 Ontology 核对业务身份、关系、索引和适用约束，选择结构化查询、直接读取、图遍历或全文/语义候选。检索候选要再次核实，不把排序或相似分数当证据。
3. 全量审计须先确定业务节点和关系的分母，排除系统内部元数据，并完成必要的分页与关系检查；查询受限时报告所检查的数量、查询条件和遗漏范围。抽样只对样本下结论；无法遍历全集时不得称“全库无问题”。
4. 来源须实际核对其可访问性、版本、相关内容和支持的**具体主张**；只见到标题、Source 节点或 Commit 定位而未读原文时，说明仅核实定位存在。来源主张本身也可能错误，关联不等于独立证实。
5. 只读取当前任务获准访问的来源。能够读取不等于可以在报告中公开全部原文；按目标读者的实际权限只展示必要的结论、可披露的证据定位与最短必要摘述，避免泄露凭证、个人信息、私有路径和未获披露许可的内容。

## 2. 按用途取证，不机械填字段

| 维度 | 检查方法 | 必须保留的区别 |
| --- | --- | --- |
| 真实性和来源 | 将重要事实拆成可核实主张，逐条对照实际材料、版本和验证范围 | 来源声称、用户报告、AI 推断、独立验证不同 |
| 完整性 | 从用户问题列出必要信息，核对属性、条件、关系、证据是否能支撑回答 | 未知可被准确保存；不凭字段为空判错 |
| 身份和一致性 | 按业务键、来源、时间、条件检查疑似重复、冲突和关系误连 | 同名不等于同身份；相反观点不等于事实矛盾 |
| 时间和有效性 | 分清事实发生、来源观察、适用期间和版本提交，查询当前结论时查现行证据 | 较新的 Commit 不证明业务事实较新；没有失效证据不等于永久有效 |
| 关联和追溯 | 沿实际关系方向、端点和属性验证被支持主张及适用条件 | 链接存在不证明来源内容支持全部断言；缺边不自动等于错误 |
| 检索和复用 | 用任务真实问题运行结构化/图/全文检索，核对答案、来源与适用条件 | 检索未命中先查索引、分页和查询范围，不等于知识不存在 |
| 内容职责与视角 | 对照类型语义、知识正文、主张依据、适用条件和维护过程，检查读者能否独立理解和更新 | 方法、来源观点、实际经历和经验结论不可混成无归属事实；必要案例过程可以保留 |

质量维度是按用途选择的观察角度，不是固定六栏必填表、通用阈值、自动加权评分或一套新的 KG OS Schema。若资料确实未记载时间/状态，保留未知并说明它妨碍了哪类使用；不倒填观察时间或臆造生命周期状态。

**证据强度要按所核实的主张区分**：

- **来源可定位**：只确认资料存在或定位有效；尚不能说其内容支持某主张。
- **来源实际支持**：检查了适用版本和具体正文，确认它陈述或足以支持该主张；这是“来源说了什么”，不必然是“现实已独立证实”。
- **独立验证结果**：当主张涉及实际部署、执行效果、测试通过或现行状态时，核对独立观察、测试与其环境、版本、范围。对于已形成的正式决定，权威决策记录可直接证明“决定已作出”，不强求运行证据证明决策存在。

原文只支持部分结论时仅承认被支持部分；来源互相矛盾时核对身份、权威范围、适用版本和时间，不按数量、发布日期或文字相似度直接定输赢。来源暂不可读、指向可变资源或版本不能确认时，将相应主张标为未验证，不推断它一定错误。原始资料明确给出了对当前用途重要的信息而 Knowledge 遗漏时，可以提出有据的补充建议；原文同样未知时不填造。

### 内容 Review 合同

先确定记录的对象、用途和视角，再选以下相关判据；不要求所有知识有步骤、案例或统一模板。每项发现指出实际内容/关系、可观察缺陷、依据与最小修正，不用总分或字段齐全代替判断。

| 检查对象 | 可观察缺陷 | 判断依据 | 最小修正 | 结果边界 |
| --- | --- | --- | --- | --- |
| 用途与视角 | 观点无归属、经历变定律、方法写成整理日记 | 本条要表达什么、来源实际说了什么、谁有可核实经历 | 恢复归属，区分事实/观点/经历/经验/方法并保留必要过程 | 来源观点可以合格；不据此承认现实结论已独立证实 |
| 独立可理解性 | 依赖“本次/本轮/这里”，离开聊天无法识别主体或情境 | 原材料可得的对象、任务/版本、业务时间和适用范围 | 补足有据语境；缺失则明确未知 | 不编造细节，也不为简短删掉必要情境 |
| 主体、时间、条件和证据 | 一份来源被用来支持另一主体/时期或更强结论 | 原文支持的具体主张及版本/范围，实际图边端点 | 缩回支持范围，逐项关联来源，保留待核主张的归属 | 未证实不等于已证伪；不能把所有转述升级为事实 |
| 事实粒度 | 多个可独立更新/引用的主张挤成一条，变动一项需覆盖全部 | 业务身份、主体、时间、条件与来源的独立变化 | 在既有模型允许的粒度分开主张或逐项表达/关联 | 不强制一句一节点；真实结构缺口交 Ontology，不扭曲正文凑 Schema |
| 正文与维护记录 | `limitations`/方法正文混入改名、键、批准、旧节点保留或未改分支 | 这些信息是否改变知识的使用判断，还是只说明如何整理 | 移除错放内容；确需留痕时用已有且获准的维护记录/提交说明 | 不自动写 VLog；本来记录系统维护事件时，相关过程可以是正文 |
| 限定与密度 | 重复告诫没有决策作用，或关键适用条件被删 | 删除该句是否改变正确使用、证据判断或风险边界 | 合并冗余；保留条件、反例、不确定性与证据限制 | 无固定字数、免责声明配额或一律客观口吻 |
| 必要完整性与使用价值 | 有主题标签但缺关键结论、条件或关联，后续使用者无法据此理解或判断 | 本条知识实际用途所需的信息，而非统一字段清单 | 补充有据且必要的事实/判断/关系；证据不足则缩小结论 | 方法需要关键判断时才补步骤，不强制所有知识都有步骤、案例或行动建议 |
| 复用与更新 | 同一身份/范围和信息被重复保存，或新信息覆盖无关内容 | 已有记录及本次实际新增、补充、纠错或现实变化 | 复用充分条目，最小增补有据变化 | 无新增价值是变更结论，不是原知识不合格；明确不同对象/记录请求另按真实身份处理 |

结论按对象和本次操作说明，可区分：

- **内容合格**：用途、归属、表达和证据强度一致；可以包含准确标注的未知、观点、计划或有限经历，不要求每条都已有外部独立验证。保存仍依实际授权。
- **需修订**：有可指出的错配、语境缺失、主张混杂、错放维护历史、冗余或模型扭曲；说明最小修正及影响范围，不泛称“质量差”。
- **证据待核**：某项更强结论或适用判断缺关键依据，指出待核主张、缺什么及目前能忠实表达到何种强度。不能阻止独立合格部分或有归属的观点/未知被保存。
- **无新增价值**：同一身份/范围已有准确充分内容，本次没有有据变化；复用即可。它是是否新增/更新的判断，可与内容合格并存，不作为主观价值门槛。

保存建议/获准写入前做内容 Review；写后按实际 State 回读对象、关系和来源，确认保存结果；使用中出现新问题再针对受影响内容处理。重复请求优先复用已核实结果，输入或证据变化才重审相应部分。只读任务不修库，结果 Review 不执行案例或模型试验；这些规范也不保证宿主/模型永远遵守或现实效果已经实证。

以下仅为合成文字对照，用于解释判据，不是待执行任务或生产材料：

| 问题表达 | 有据时的修订方向 | 保留的边界 |
| --- | --- | --- |
| 方法限制写“本轮已改名、用户批准保存、旧条目保留” | 方法保留适用条件；整理经过按需要另作获准的维护记录 | 若正文对象本来就是一次维护事件，其改名/批准过程可以相关 |
| 经验写“本次先核对就成功了，以后都这样” | 交代何种任务/环境、核对了什么、有何观察及可迁移范围 | 无法证明普遍有效时保留为有界经验，不伪造时点或效果 |
| “甲批准、乙交付、丙验收”，只引一份批准通知 | 分别表达批准、交付、验收及各自实际来源；缺证据的项目标为未知/来源主张 | 批准通知不能单独证明另两个动作完成，不强制每句建节点 |
| Claim：用途是判断导出是否保留关系，却只写真实的“工具 X 支持导出” | 表达当前只确认有导出功能，关系保留能力未注明；有来源后再补所需能力与限制 | 事实可真实但不足以支撑该用途，不猜测缺失功能 |
| Procedure：有“目标/步骤/结果”三栏，但步骤仅是“打开工具，点击处理” | 对合成去重任务说明先按已核实业务键比较；同名不同键保留，键未知标待核，再处理确认的重复 | 结构齐全不等于可执行；不强制其它知识类型套三栏 |
| Case：原材料只记工具 X 在离线样本的一次成功，简写为“该方法可靠” | 保留版本、离线/样本范围、一次观察及结果，不据此断言普遍可靠 | 简洁不能删掉决定适用范围的条件，也不能补造未记版本 |

## 3. 审计步骤与问题验收

- **确定验收问题**：从知识的现实用途选择能区分成功/失败的提问，例如“某决策为何成立、适用于哪个项目、依据哪个固定版本”“某故障采取了哪项措施且经何种独立验证”。无关问题不应成为必过门槛。
- **执行取证**：在固定 State 读取对应 Knowledge 与必要关系；对受影响身份、重复候选、时间/适用范围及来源做定向核对。需要全量枚举时完成分组计数与必要分页；引擎一致性只证明存储/约束，不证明业务真实性。
- **验证答案**：核对查询是否找对对象、来源是否支持关键主张、关系是否支持推论、答案是否保留版本和限制。对失败定位为内容缺漏、证据不足、关系错误、检索/索引覆盖或未知，不一律提出改模型。
- **形成发现**：逐项分类为「已证实问题」「待核实风险」「合理差异」「未检查/证据不足」。缺少决定性来源时，不能把“待核实”升级为“事实错误”；已确认矛盾也不自动表明哪一方为真。
- **提出改进**：说明目标对象/关系、业务影响、依据、最小动作及可核实的验收问题。只读任务到此结束；获具体授权后由 Knowledge 做最小修改并回读，只有真实模型表达缺口才交给 Ontology Skill 提案。

### 审计覆盖、深度和成本

- **结构覆盖**：枚举了哪些业务节点、关系、来源和版本，实际分母与未读分页是什么；内部元数据不计入业务数量。
- **语义深度**：哪些主张核对了原始资料，哪些只核对了来源定位、字段/关系或抽样，哪些没核实。完成结构全量盘点不代表所有主张通过真实性审计。
- **使用验收**：哪些代表性问题实际运行、是否获得有证据且范围正确的答案；没有执行的测试不得标通过。

按任务和风险由结构扫描定位候选，再对会指导行动、可能造成错误决定或影响多人/多系统的主张优先深查；简单目录项或已经充分确认的低影响知识可有界收口。发现已证实的高影响错误优先于纯格式空缺，但不以影响程度替代真实性判断。用户明确要求逐条完整核对时必须完成约定深度，不能悄悄改为抽样；资源、权限或时间受限则准确交付部分覆盖和剩余范围，不宣称完成。不要为凑固定覆盖率或分数反复读取无关资料。

## 4. 容易误判的场景

| 场景 | 合格判断 |
| --- | --- |
| Decision 缺少日期，原始资料也未注明日期 | 报告发生/生效时间未知及其用途限制，不自行补日期，也不直接判事实错误 |
| 决策正文明确记载日期，而相应字段为空 | 核实日期是否属于该决策及其业务语义，报告有据的表达缺漏并建议最小补充；不把所有空值统一判错 |
| 两条 Knowledge 名称相同，但身份键/来源或有效期不同 | 先核对是否同一业务身份和条件；不能直接合并 |
| 两份报告结论相反，但各自适用条件或来源不同 | 保存双方主张及作用域；同一条件下确实互斥才是冲突候选 |
| 已有 Source 与关系，检查原文发现不支持所连主张 | 指出具体不支持之处和受影响的关系；不能以有引用即通过 |
| 原始材料只证明镜像构建完成，Knowledge 写“已部署且验收通过” | 源材料只能支持构建完成；部署与验收需另外核实，不能把未验证当成已证实失败 |
| 全库请求只取到第一页或语义 Top-K | 报告已检查页/样本和未覆盖部分，不宣称全量无缺陷 |
| 数据库 consistency=valid，某条“已验证成功”来自自我描述 | 结构检查通过，但事实效果尚未独立核实 |
| 重要决策可按标题找到，却无法追溯实际支持依据 | 检索存在不等于使用验收通过，识别证据/关系缺口及具体影响 |
| 某次审计没有发现问题，且用户未授权保存 | 报告实际覆盖和零发现，保持知识库不变，不自动写 VLog |

## 5. 报告质量与停止边界

按任务输出**目标 Instance/Branch/State、结构覆盖、实际语义核验深度、真实使用问题及结果、重要发现与可披露依据、未检查的限制、建议动作**。有数量时标注真实分母和计数单位；只对确认的对象下结论，不套用固定分数或伪精确百分比。按受影响知识的用途优先呈现重要问题，不默认公开证据原文、私有路径或敏感字段。发现为零可以是完整结果；不为了制造整改任务重复检查或扩大范围。

| Google Technical Writing [Documents](https://developers.google.com/tech-writing/one/documents)、[Clear sentences](https://developers.google.com/tech-writing/one/clear-sentences)：正文脱离聊天后是否成立 | 确认使用者目标、已有知识、必要前提与范围；主体/动作/条件明确，正文与明确关联足以理解。结论和必要条件前置 | 不要求每条复制背景/受众字段；不编造数字、效果或已知前提来显得准确 |
| Diátaxis [Compass](https://diataxis.fr/compass/)、[How-to](https://diataxis.fr/how-to-guides/)、[Quality](https://diataxis.fr/quality/)：内容究竟服务理解、查证还是行动 | 先确定实际使用目的；方法按目标和必要判断/行动组织，允许条件分支；真实性、必要完整性和使用价值分别判断，完整准确也可能不满足当前用途 | 不强制图谱采用四类文档，不把原文的纯行动分离原则变成禁止方法中保留必要解释，不将所有事实条目写成教程 |
| Microsoft [Scannable content](https://learn.microsoft.com/en-us/style-guide/scannable-content/)：能否快速找到关键结论和条件 | 标题/首句先给有关信息；同类项目用平行表达，长内容按实际问题分段，删去无决策作用的重复 | 不复制网页布局、行数、字号或设备阅读规则，不为短而删掉条件，也不为每个节点强制加标题层级 |

这些方法支持上述文本 Review 合同，不证明其在指定模型/宿主上已稳定改善知识质量；写后回读只能核实实际保存状态，使用效果需对应证据。以下原有来源补充证据、追溯与审计维度，不替代内容用途/视角/结构判断：

- [W3C Data Quality Vocabulary (DQV)](https://www.w3.org/TR/vocab-dqv/)：借鉴按使用目的选择维度、将维度与具体评估方法分离；不引入 DQV/RDF 本体或固定权重。
- [W3C PROV-O](https://www.w3.org/TR/prov-o/)：借鉴事实来源、活动和责任归属及版本衍生的区别；不强制创建 Entity/Activity/Agent 节点。
- [W3C SHACL](https://www.w3.org/TR/shacl/)：借鉴目标范围、约束和逐项验证报告；KG OS 使用当前 Property Graph/Constraint，不声称原生支持 SHACL。
- [FAIR Guiding Principles](https://www.nature.com/articles/sdata201618)：借鉴可发现、可获取、可互操作、可复用，特别是稳定身份与来源；不机械加入科研数据许可字段。
- [Quality assessment for Linked Data: A Survey](https://journals.sagepub.com/doi/10.3233/SW-150175)：质量与用途相关，涵盖真实性、一致性、完整性、时效及可理解性；不用通用分数代表知识可信。
- [Great Expectations validation](https://docs.greatexpectations.io/docs/core/run_validations/)：借鉴期望条件、实际验证结果和失败对象清单；不引入额外运行时框架。
- [Wiki Audit Skill](https://github.com/kfchou/wiki-skills/blob/main/skills/wiki-audit/SKILL.md)：借鉴按主张核对引用是否真实支持、标出无证据主张；不把其 Wiki/脚注或并发子 Agent 流程直接移植到图谱。
- [Knowledge Base Optimizer Skill](https://github.com/craviart/knowledge-base-optimizer/blob/main/SKILL.md)：借鉴盘点结构、来源真源和非破坏性纠错；不引入其文件备份、路径搬迁与知识库重组工作流。
