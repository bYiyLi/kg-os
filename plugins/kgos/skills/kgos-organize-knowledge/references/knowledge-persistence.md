# 保存与恢复

仅在主流程已完成检查和授权核对、准备写入时读取；先前写入结果不明时，也用本文件恢复。这里负责“怎样安全保存并取得实际结果”，知识是否合格由质量检查资源判断。

## 1. 读取当前接口合同

通过 `kgos_docs` 读取以下文档，适用于当前连接版本的已读文档可以复用：

- `guides/objects.md`
- `guides/evolution.md`
- `guides/errors.md`
- `sdk/object/readText.md`
- `sdk/object/patch.md`
- `sdk/types/PatchRequest.md`
- `sdk/types/PatchResult.md`

普通 Knowledge 变更使用 `object.patch`。输入是根据实际 canonical 对象文本生成的精确 Git Extended Diff，不是 JSON Merge Patch。不要执行文档中的建模或故障注入示例。

## 2. 核对基准并生成补丁

写入前用 `evolution.get({state:"branch/"+branch})` 重新解析同一目标分支。

- Head 仍为 `baseState`：在该 State 读取拟修改或删除对象的完整 canonical body。
- Head 已变化：以新 State 重读受影响定义、对象和关系，重新核对身份、冲突、影响和授权，重做受影响的保存前检查；通过后把 `baseState` 更新为新 State，再生成补丁。

不能把旧补丁直接重放到新 Head，也不能只换 `baseState` 而不重读内容。

已有对象用实际 Ref；新对象用当前合同规定的请求内 alias，成功后再取得永久 Ref。别名不是生产业务键，也不是可猜测的永久引用。

必须同时成立的节点和关系变更放在同一次 Patch 中。删除节点时明确处理相关关系，不能假定系统自动级联删除。若接口限制使必要联动无法原子完成，说明限制和部分完成风险，请用户决定处理方案，不擅自留下不一致状态。

## 3. 执行并检查回执

通过 `kgos_mutate` 调用 `object.patch({branch,baseState,patch,message})`。`branch` 使用已确认的裸分支名；补丁只包含变更清单中检查通过且获准的内容。

按 `guides/evolution.md` 编写本次提交说明：简介概括已核实的知识世界与用途，改动只写本次实际变化。无变化时不额外创建 Commit，也不为补写说明另建 Commit。

检查外层 envelope 的 `code` 与实际 SDK 返回结果；脚本正常返回、HTTP 200 或 `isError=false` 都不能单独证明写入成功。

成功后保留返回的 `state`、`created` 和 `transitions`，据此取得新对象正式 Ref 和身份变化。单次 Patch 的原子性不扩展到多个 SDK 写入或后续回读。

## 4. 处理失败或结果不明

- `PATCH_BASE_MISMATCH`：重读所用不可变 State 的完整 canonical body，修正精确补丁及换行，不做模糊匹配。
- `STALE_BASE_STATE`：返回第 2 节，重读目标 Head、受影响内容并重新生成补丁。
- 身份、对象或依赖冲突：核对实际对象和差异，未解决前不写冲突项。
- 权限拒绝：保留原目标和已知结果，报告被拒绝的操作与所缺权限，不换实例、分支或渠道绕过。
- 超时、断线、取消或缺少回执：先读取实际目标分支的 Head、相关历史和目标对象，确定哪些变更已生效。历史方法按 `guides/evolution.md` 及所用方法文档读取，不猜接口。

已生效部分不重做；只有确认未执行、当前状态仍满足原意图且授权有效的部分才可继续。仍不能确定结果时，暂停可能重复或破坏数据的动作，报告已确认、未知部分及所需证据。重新授权不能代替执行结果核实。

修复需要新目标、更大影响或受保护操作时，交回主流程确认；不能把失败恢复扩成未获准的外部系统维护。

## 5. 取得可核对的实际结果

在本次写入返回的不可变 `state` 中：

1. 用 `object.readText` 回读新增、修改且仍存在的对象与关系，使用返回的正式 Ref。
2. 删除目标单独核验，不混进要求所有 Ref 存在的批量回读。在能够覆盖目标及相关端点的获准范围内，按已确认身份执行当前接口支持的只读存在性查询，并核对关联处理结果。查询失败、不完整或目标不可见，不能判定删除成功。
3. 若本次创建了 Commit，用 `evolution.get` 回读该 State 的实际 Message，核对说明与真实变化。并发产生的新 Head 不能代替本次结果。

将实际内容、关系、删除检查及回执交给主流程进行保存后质量检查。回读失败只说明结果尚未核实，不抹掉已确认的写入，也不把计划内容当作实际结果。
