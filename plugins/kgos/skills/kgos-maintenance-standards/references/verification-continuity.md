# 结果验证、恢复与长期连续性

验证维护任务的真实结果，不用“命令返回成功”“产生Commit”或“已建议处理”替代质量改善的证据。核对范围与任务对应：局部关联修正通常不需要全库重新扫描；全库治理也不能只验证一个样本就宣称完成。

## 前后状态与影响

在实际权限内核对目标Instance、Branch和变更前后返回的不可变State。比较任务受影响的对象、真实关系及必要Ontology/Constraint；有意跨历史比较分别标注State。实际Diff有助于发现意外删除或结构变更，但不证明更正事实可信，也不保证业务语义和外部环境已验证。

| 验证对象 | 需要回答的问题 |
| --- | --- |
| **原质量问题** | 先前基于什么判定问题成立？现在相同范围/适用条件下是否不再成立？ |
| **身份与关系** | 保留了该保留的来源、角色、关系端点与历史事实吗？是否形成新的误合并或断链？ |
| **影响与无关内容** | 是否误动未授权对象/关系、模型/索引或其它Branch？实际证据覆盖到哪里？ |
| **操作真实结果** | 是建议、成功写入、写入后回读通过、部分失败还是结果未知？哪项未核实？ |

补充一个字段不应使其它字段消失。多个同名候选经过身份核对后决定保留，也可以是完成了维护判断而未执行写入。修复某个节点成功，但其错误关联仍在时，不得认定该目标问题已经完整解决。

## 无变更与未验证分别对待

当本次范围内的检查充分且没有确定问题，维护可以以**有界无修改结论**完成；如用户已授权每次运行记录，向VLog提供真实检查时间、目标和覆盖/遗漏，但VLog的记录内容、写入身份/证据质量由VLog规范负责。没有变更不等于没有执行维护，也不等于全库无问题。

检查失败、只检了一页或权限不足时，明确列出已查、未查和不确定项，不能因为没有确认问题就把剩余部分标为通过。部分对象已修正、其它对象未决时，分开报告，不让单一“done”标签遮蔽未完成的目标。

## 并发、未知回执和恢复

Object Patch目标Branch可能被别的工作推进；旧baseState提交被拒绝时，读取实际新State后核对新变化与原意图，不能自动重放删边/覆盖字段。Graph Execute、Merge Session和多次API调用没有统一可假定的事务边界；具体实现按实际合同判断。

取消或丢回执后，先读取实际Branch Head、已知Object身份、History和必要Diff；失败、未执行、已经提交、结果仍不明是不同情况。确定已完成的工作不重新执行；未知项只暂停可能产生重复或破坏的动作，不把之前已独立验证的结果也声明回滚。读到某个对象已符合目标，不自动证明是哪次丢回执的调用导致它符合。

发生未授权范围外的变化，不以“维护需要”作为恢复权限去Reset、清历史、移动Tag或删除分支。需要模型修改、跨世界搬迁、VLog保存或外部调度时分别按实际授权及所属合同继续，不用本规范替代。

## 持续维护而非无限重查

以前的真实维护结论、未决项和复发问题可指导下次检查聚焦何处；历史结论只对当时State、业务时间和检测范围负责。若本次风险范围已变，调整检查边界；若前次疑点已被充分排除，不每次再强迫复查同一全库。

有可靠运行来源时区分计划、实际运行、完成、记录/验证时间；最近VLog更新或最近Commit不意味着今天执行了巡检。调度频率/任务启用属于外部平台，`kgosd`本身没有维护Scheduler。维护可以按用户临时触发，不要求创建计划或固定频率。

停止检查的条件是当前任务的已知目标和证据要求得到满足，或明确说明受限与仍未解决的部分；不是候选清零、数据库没有任何差异，也不是人工凑出一个高分。保持本次宿主任务实际交付，不创建独立维护报告格式或无限反思循环。
