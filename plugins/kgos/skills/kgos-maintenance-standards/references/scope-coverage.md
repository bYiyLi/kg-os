# 维护范围与证据覆盖

明确范围是为了避免用局部发现宣称全库质量，不是要求每次都做全量扫描。对用户明确的“一批已知对象”，优先核对这批对象及相关约束；对“整理整个知识世界”，按模型、业务场景及实际可访问范围组织有界检查，不能把只看首批记录解释为完成全库整理。

## 定位实际目标

确定可访问的 Instance、Branch、所比较的 State、业务时点及所针对的模型/实例。Domain 是 Ontology 的组织，不是天然的数据分区；“只维护学习 Domain”需要根据真实 Definition 和实际查询条件确认数据范围。多个 Branch 各代表独立 Snapshot，不因同名节点就合并其数据；跨世界归属与演进属于 Branch 决策。

只读检查一组相关对象时固定同一个返回的 immutable State；有意比较旧/新版本应分别标识。Branch Head 后来移动不能悄悄把两次读取当成同一快照。业务事实的有效时间与 Commit 时间不同，指定“过去有效”的维护评审不能只按最近Commit筛选。

## 从任务目标决定检查充分性

| 本次目标 | 需要取得的证据 | 何时应停止 |
| --- | --- | --- |
| 已知一条错误关联 | 端点、方向、关系语义及其直接受影响对象 | 已确认范围内问题/非问题、处理方案及影响，不扩成全库审计 |
| 查找某稳定键的重复 | 作用域内全部可达候选，按真实键/身份定义判断 | 已覆盖该键的可信查询条件、分页及目标约束 |
| 调查某类系统性重复/过时 | 实际模型、索引和明确查询范围；必要时分页/抽样及抽样方法 | 充分判断请求范围，或准确报告受限/未覆盖部分 |
| 用户要求完整库维护 | 按已定义业务目标覆盖可访问模型与实际知识，分别记录未读页/连接/分支 | 真实覆盖全部已约定范围；无法完成时保留部分结论，不虚报全库完成 |
| 定期巡检、没有变更 | 当次Run的目标、实际检查集合、时间、未检查范围和结果 | 完成约定检查即可，不强行制造一个要修的问题 |

没有通用的“检查100条”“每周一次”或每个类型都要FTS+Vector的固定标准。真实数据可能很大，发现问题后只补读与该问题相关的必要资料。已足够确认结论时停止；需要证明“范围内不存在重复”则不能只用受截断的候选集、第一页、Top-K或故障时的空结果。

## 查询证据的边界

依实际 Ontology/Graph 选择可表达的查询。向量或全文相似命中仅用于生成候选，不足以证明身份相同；相关Index未覆盖字段、NULL处理、排序/limit和图路径重复行会影响统计结论。检索基础能力的策略和准确查询语法由 Retrieval/Graph owner 负责，不在Maintenance另建DSL或复制SDK手册。

读取失败、超限、取消、权限不足时保留实际已核实的部分。零结果可能意味着真的没有、条件错误、未检索覆盖或运行失败；结论必须限定在正确的证据范围。明确的检查目标若因能力不足而不能完成，说明缺什么以及已完成哪些，不自动扩大权限或循环重试。

## 防止“维护”越权

只读评估时不运行临时写入来“测试约束”，不为备份创建Branch/Tag，也不自行修改全文或向量索引。系统是否连通、官方Skill是否安装、定时任务是否启用，属于Doctor/宿主平台；这里仅在它们影响当前检查证据时说明限制。

既有维护记录可帮助选择本次范围，但旧VLog没有自动覆盖真实现态。目标已经明确且足够判断时，不因维护概念要求全库再扫描一遍。
