# 维护处置的选择与最小影响

处理目标是让已确认的问题不再成立，同时保留其它真实、有价值的知识；不是让对象数量最少或让所有字段一致。维护措施须匹配问题原因、任务授权、可用模型及实际影响范围。

## 对不同问题作不同选择

| 已有依据 | 候选处理 | 不应自动进行 |
| --- | --- | --- |
| 信息仍正确，只是名称/分类混乱 | 维护实际显示值或补充已证实说明 | 删除事实/改变模型身份 |
| 确认同一业务对象有多条实例 | 根据身份、关系和来源评估安全整理、复用或合并表达 | 直接删除一条，假定所有关系自动转移 |
| 对象同名但身份不同，或主张条件不同 | 保持独立，必要时补充区分信息 | 因“重复”一律合并 |
| 某已确认字段/关联错误 | 在已授权的目标对象上局部纠正，并核对关联影响 | 重建整个世界、覆盖其它属性 |
| 同一目标在当前条件下事实冲突，来源尚不能裁决 | 保留各来源与未决，不将猜测写成确定值 | 根据新旧时间、分数或最后写入选赢家 |
| 已确认模型不足以表达有用事实 | 指出具体无法表示的语义需求；宿主另有模型调整授权时按Ontology处理 | 私自新增通用status、Claim、Source等字段/Node |
| 老记录仍是准确历史，当前规则已变化 | 保留历史并按真实时间范围表达新事实 | 将历史正确知识清理掉 |
| 本次限定范围内没有问题 | 保留原状，按实际范围交付检查结果 | 为显示“维护有产出”制造修改 |

“合并重复节点”在KG OS中不是通用 `maintenance.merge` API：删除或替换Node可能影响它的关系、来源与历史对象Ref。按现有Knowledge/Graph/Object合同确认需要迁移/重连的实际边及版本变化；无法保留必要信息时停在方案/未决，不执行危险部分。跨Branch整体Merge更不是实例去重；若确有实验隔离需求由Branch标准判断，不将每次维护强制送到新Branch。

## 对权限与并发保持精确

只读审查不修改记录、修复索引或清除VLog；“检查并修复已证实问题”的授权也不必然包含批量删除、多库迁移或重写Schema。已授权的局部修改不要求每个普通字段重复批准，但影响范围实际扩大时需要真实授权依据。

用正确目标Branch、不可变baseState及本次确认的对象/关系内容实施已授权Patch。错误内容若与新证据矛盾，重新读取后作决定；不能仅更新baseState并重放旧整体内容覆盖他人并发工作。Graph Execute不自动继承Object Patch的事务/基线检查行为，遵循实际API，不自造互斥锁、暗中低层Reset或自动快进。

多个对象有依赖时可在现有公共合同允许且符合任务要求的范围一次原子Patch，不强迫所有维护使用一个全库事务。多次独立调用不可假定一起回滚；一部分已保存、一部分失败或结果未知，分别核对后续，不重试已经成功的副作用。

对缺失来源、未决身份或缺少模型的部分可以不改；能够独立安全处理且已获授权的其它部分可继续。将拒绝处理危险部分与全面否定用户任务区别开来。

## 防止扩大业务定义

维护发现模型约束与实际业务不匹配，可以给出最小的模型需求与受影响样例；具体Definition/Constraint/Index方案由Ontology owner负责。常规已知错误的实例值/关系改动仍由Knowledge owner负责。Maintenance保留对**哪项维护值得做、是否处理充分**的判断，不复制其完整内容规范。

不得为检查正确性发明QualityScore、MaintenanceIssue、Archived、PendingEntity通用Schema或后台队列。若用户所在领域已有类似模型，按其真实含义使用；名字相同并不授权把本规范的三种判断固化为其枚举。
