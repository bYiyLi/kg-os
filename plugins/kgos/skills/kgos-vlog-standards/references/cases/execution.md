# 案例：事件、执行和结果

应用 [执行结果与证据](../outcomes-evidence.md)。E1–E3使用给定模型 `ExampleVLog`：entryKey为记录唯一键，eventKey标识事件，runKey标识已知执行，narrative可完整表达过程与证据，所有字段为STRING。entryKey是本记录库的身份，runKey来自本例已确认运行源；此结构只是已有模型的教学前提，不是官方Schema或SDK请求格式。

## E1：同一故障两次尝试，不把失败覆盖成成功

事件INC-1的第一次尝试RUN-1被服务端明确拒绝；第二次RUN-2已应用修改，但指定环境复测仍失败。用户授权按既有模型记录两次执行。两者属于同一故障，不是同一次Run，更不是两次成功。

### first-attempt

```json
{
  "labels": ["ExampleVLog"],
  "properties": {
    "entryKey": "L1",
    "eventKey": "INC-1",
    "runKey": "RUN-1",
    "narrative": "第一次尝试被服务端拒绝，未应用修复；依据：RUN-1拒绝回执。"
  }
}
```

### second-attempt

```json
{
  "labels": ["ExampleVLog"],
  "properties": {
    "entryKey": "L2",
    "eventKey": "INC-1",
    "runKey": "RUN-2",
    "narrative": "第二次尝试已应用修复，但测试环境T复测失败；依据：RUN-2操作回执与TEST-2结果。"
  }
}
```

验证要分别回读L1/L2及其事件/执行归属；写入成功不证明叙述是真的。错误示范是给事件统一填“完成”并抹掉RUN-1，或复制所有调试输出却不说哪次验证失败。若已有模型是一条事件概要，可在概要内保留两次尝试的区别，不要求照搬这里的两节点形式。

## E2：后来补充验证，记录此前失败仍然发生过

明确证据说明RUN-2修复后的环境T在排除独立测试依赖故障后通过TEST-3，前次TEST-2确实失败。现有任务允许补充L2，不把TEST-2改成从来通过，也不自动创建另一次修复执行。

### verified-followup

```json
{
  "labels": ["ExampleVLog"],
  "properties": {
    "entryKey": "L2",
    "eventKey": "INC-1",
    "runKey": "RUN-2",
    "narrative": "RUN-2修复已应用；此前环境T的TEST-2失败，后续TEST-3在同一修复版本通过。此次补充验证结果，不新增修复尝试。"
  }
}
```

核对L1不变、L2当前文本保留此前失败与新证据、旧State仍可回读原L2。相邻条件：如果TEST-3测的是另一个代码/知识版本，不能据此认证RUN-2的原结果，应准确关联那个版本；发生独立新修复尝试时也须按新Run处理。

## E3：报告“成功”是错的，不是后来发生了回退

旧记录误把另一环境的通过报告当作本环境验收。收到明确证据后纠正当前结论，说明原认证无效；不能写成“曾验证成功、后来失效”这种未发生的状态变化。旧历史保存错误记载不等于它曾是真的。只有无法裁决的两份报告才保留冲突，不把已证明的抄写错误永久等权并列。

## E4：未知回执与未执行不同

外部操作已发出但断线，不能说操作已回滚；记录请求已发出和结果未知及实际定位。后来核实目标已达成，可以补充观察，但除非有归因证据，不认定是那次调用造成。为了写完整VLog不能重跑可能重复的业务操作。

只有计划未发出时记录计划；明确失败回执时记录具体失败。用户说“我已验证”可保存为用户报告，不能变成AI亲自运行的独立验收。

## E5：周期任务和最新编辑时间

昨日Run实际通过，今天只修正记录错字。最新VLog Commit不能证明今天维护运行过。只有外部平台显示计划启用也不能补造今日Run；反过来一条记录暂缺不能证明没有运行。保留可访问证据与未知边界，不用当前时间填缺失的执行时间。
