# KG OS Doctor · 线性增量报告模板

本文件是 Doctor 的**输出合同**：完成一个适用检查，就交付该项的结果与证据；不是要求 AI 先填满报告、增加诊断项目或执行写入。实际诊断规则仍由 `SKILL.md` 和对应检查参考负责。

## 1. 展示顺序

- 开始时用一句话交代**本次检查范围**、已确认的目标连接/Instance/Branch（若适用）及实际发行基线；未知就说明未知，不为填字段猜测 State、版本或时间。
- **必须按 D1 → D2 → D3 → D4 → D5 的顺序展示结果**。全面诊断覆盖五项；定向诊断只展示本次请求的项目和确有必要的前置结果，**不得为了填满模板执行或显示其它项目**。前置读取若仅用于目标检查，可在该项证据中交代，不必另建一个无关报告段。
- 在宿主支持当前会话中途输出时，**每项获得证据支持的结论或明确受阻后，立即输出该项**，然后继续后续检查。可以并行取得独立检查的证据；固定的是**展示顺序**，不是工具执行顺序。已完成的后项先保留结果，按前项展示或明确受阻后再输出，不让等待不可能取得的证据无限阻塞。
- 宿主不支持中途交付时，最终回复依同一顺序**一次性线性呈现**，禁止声称已经逐项实时输出。除后续证据要求更正外，**已交付段落不再重复**。
- 同一项目涉及多个 Instance/Branch 时，按已核实的目标分别说明状态和 State；不可将一个目标的 `PASS` 推广到其它目标。

## 2. 单项结果片段

每次输出一个项目时使用以下**结构**，只填入实际证据。占位符是编写指引，不允许原样出现在正式报告：

```text
### Dn · 检查名称 — PASS / WARN / FAIL / UNKNOWN
范围：实际可观察的宿主 / Instance / Branch / State（按此项目适用）
证据：实际调用、返回事实或可信来源；UNKNOWN 时说明确切缺少的证据
结论：该证据能证明什么，哪些范围未检查或仍无法判断
建议：只有确认缺口或可行动的未知事项时才给出最小下一步
```

- `PASS` 需要当前适用范围的真实成功证据；`WARN` 与 `FAIL` 必须有对应事实；`UNKNOWN` 说明是访问受限、依赖失败还是不可观察。不得用 D2 的 State/Ontology 读取成功替代 D4 Knowledge 查询成功，也不得将未执行的依赖检查重复报告为 `FAIL`。
- **不适用**是事实说明，不是新的健康状态；明确不适用时简短写明原因，不填虚构的 `PASS`。未请求项目直接省略。无问题时省略“建议”，不输出空标签或大段格式占位。
- 一个段落只陈述本次实际检查结论；多个子项确有不同状态（例如引导加载与行为、任务执行与 VLog 验证）时，分别说明，不为它们捏造共同状态。必要的证据定位与限制比格式整齐更重要。

## 3. 依赖失败与结果更正

- 例如 D2 认证失败：**D2 = FAIL**；D4 若因依赖而无法执行，写 **D4 = UNKNOWN（受 D2 阻塞）**。独立的 D3 应继续检查并单独报告，不因 D2 失败宣布全部诊断失败。
- 若前项无法得到完整宿主证据，但已确定不可观察，则将该项明确报告为 `UNKNOWN` 并继续；不得等待缺失证据来阻塞其它结果。
- 后续证据推翻已交付结果时，只追加**“更正 Dn”**，说明原判断、实际新证据与修正结论；不要悄悄覆盖或重新输出完整报告。

## 4. 结束语

适用项目都已经输出、或明确不可执行且独立检查完成时，只用一两句话说明**最重要的已确认缺口和仍未知的事项**，例如“诊断结束：已确认 D2 连接失败；D4 因此未能核实，D3 已独立检查”。如果全部在所检查范围内正常，则一句话报告该范围结果，不宣称全库或其它客户端均健康。

**禁止**重新生成一张重复 D1–D5 的总结表、无证据综合分数、修复成功宣称或未执行任务的完成宣称。Doctor 的只读职责在此结束，已授权的后续修复由宿主继续。
