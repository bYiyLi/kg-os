# 案例：数据库版本和业务时间

应用 [State与时间](../state-time.md)。S1、S2是叙述代号，实际请求必须用真实返回State；不是可以直接发送的Commit字符串。以下对象及日期均为合成案例。

## T1：移动分支上的两次成功读取可能不能拼在一起

S1中状态为planned；另一任务提交后S2为implemented。先在branch/main读到S1的列表，再在branch/main读到S2的详情，单次调用都成功也不表示合并结果属于同一版本。

依赖同一事实的一组读取复用S1；需要最新则重新观察并以S2完成相关判断，不把旧页和新页混合。问题明确是“比较前后变化”时分别读取S1、S2正是正确方法，不强求同一个State。

### versioned-status

下列查询的JSON描述S1预期；隔离验证会在S1与S2分别执行，S2返回implemented，然后确认再读S1仍为planned。

```cypher
MATCH (r:RetrievalStatus {key:'D'}) RETURN r.status AS status
```

```json
{"columns":["status"],"rows":[["planned"]]}
```

不从这些状态文字直接证明真实部署；本例仅说明版本读取的一致性。前后语义或模型变更时，还需各按对应State解释。

## T2：新录入的规则未必当前生效

当前快照同时保存旧规则V1（2026-01-01至2026-11-01）及提前发布的V2（2026-11-01起）。该模型明确使用日精度半开区间，缺截止表示已确认开放结束；不是所有领域默认约定。用户问2026-10-20适用版本，应按业务有效期而非最新Commit选择。

### effective-rule

```cypher
MATCH (p:RetrievalPolicy)
WHERE p.validFrom <= date('2026-10-20') AND (p.validUntil IS NULL OR date('2026-10-20') < p.validUntil)
RETURN p.key AS policy ORDER BY policy
```

```json
{"columns":["policy"],"rows":[["V1"]]}
```

相邻情况：模型允许“截止未知”时，不能套用上述null解释；需要按那个模型区分可确定有效与未知。用户问“10月20日时库里知道什么”则还需相应历史State，今天的数据按日期筛选不等价。

## T3：多库不是一个快照，也不共享所有身份

库A和库B都返回`n:7`或同名项目，不证明同一个实体；即使Commit字符串相同也不能据此证明物理库同一。分别保留实际连接、State和对象作用域，按可信业务身份对齐。不能编造跨库原子读取，也不能仅因多库不存在全局快照就拒绝用户明确要求的带时点对照。

## T4：最新记录与当前实况

知识库最后保存“昨日测试通过”，用户问“当前工作树测试通过吗”。可以将旧记录作为背景，但必须检查对应当前事实来源，不能把查到的历史成功变成今天的执行结果。无权或无工具运行时只报告未核实当前，不假装运行，也不自动部署/重测用户未授权的受保护环境。
