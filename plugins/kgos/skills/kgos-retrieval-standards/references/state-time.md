# State、业务时间与多来源读取

State 用于确定“读取哪个数据库版本”；业务时间用于解释“记录说何时成立”。本规范只管理读取一致性，不决定分支组织或合并策略。

## 固定正确目标，不固定错误默认值

从已授权任务和实际连接确定知识库/Branch/Tag/Commit；用户指定目标时不能以默认分支替代。当前 Graph 单次 query 在开始时解析 at并返回实际 immutable commit，关联后续读取复用该返回State，而不是各自重新解析移动的Branch。模型解释、索引和实例应属于对应的同一快照。

已有同一任务、同一State且足够完整的读取结果可以复用。新任务要求“最新”时重新观察目标Head；旧会话缓存不能冒充本次观察。完成当前快照的回答不要求不停重读Head直到分支永远不动，必要时说明观察时点/State。

Ontology概览的分页必须保持State和scope；MCP预览行窗口按实际viewRevision固定视图，不能把viewRevision当Graph State。如果缓存缺少版本或范围信息，就不能据此证明与新查询一致。无法核实版本只影响依赖一致性的结论，不编造Commit。

## 合法的多State场景

比较历史与现在时，分别读取明确的S1/S2并标识各自结果，允许不同快照；不为了“一致”拒绝历史比较，也不把两套值拼成曾经同时存在的状态。期间模型名称/含义变化时按各自State理解并说明可比性限制，不能用新Definition悄悄解释旧字段。

跨知识库时记录每个实际连接的身份、State和可见范围；同名对象甚至相同元素Ref/Commit字符串都不证明它们是同一物理库或业务对象。必要的跨库实体对齐依可靠业务身份证据，不能靠名称或相似度直接连接。独立读取多个库不产生跨库原子快照，时间错位会影响结论时明确说明。

## “最新”“当前”“当时”分别解释

最新录入/修订不必是最新业务事件，更不必已生效。按真实模型区别发布时间、观察/采集、事件发生、有效区间和数据库提交。未来生效规则可已存在于当前State；过去生效规则也可能后来才补录。

查询“4月适用规则”通常按业务有效时间筛选；查询“4月时库里已经知道什么”需选择对应历史数据库State，不能只拿今天的数据按日期筛选。没有明确可解析的时间或版本证据时说明差别，不用最近Commit时间填补缺口。

区间按已定义的边界、时区和精度判断，不自行给所有领域套用半开区间。缺结束时间可能是未知而非确认开放结束；“还没看到失效”不等于永久有效。引用状态本身是何时观察、适用何环境/版本同样影响“现在”的结论。

用户要求现实最新事实时，知识库结果作为带时间的已有记录；需要仓库、当前运行或其它权威源时按宿主能力/权限核实。外部查询不可用就保留“库中最后记录”与“现实未核实”的区别，不自动联网或越过用户限定范围。
