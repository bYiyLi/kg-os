# 建模决策与关键语义

只为当前需求选择表达方式。本文件约束选择依据，不提供固定领域 Schema，不替代当前连接的 `kgos_docs`。若技术示例与实际连接版本冲突，先核对该版本手册，再报告差异；不要通过猜测扩展字段让请求“看起来能用”。

## 复用、扩展或新建

比较概念的**实例范围、身份、生命周期、关系角色、约束**，而不是只比较名称。已有 Definition 能准确表达时优先复用；只是缺一个确有需求且与原义相容的字段时考虑扩展；扩展使旧实例获得错误含义、破坏键的范围或混淆不同生命周期时，考虑分开。

只看到 Ontology 第一页不证明没有相关模型。先通过目录和准确 Ref 定位候选，必要时补分页；范围未覆盖就限定“尚未发现”，而非创建同义重复类型。没有用户实例并不证明一个类型无用，它可能服务尚未写入的数据或查询合同。

## Node、Relationship、Property 与中间对象

| 情况 | 合理选择 | 必要的反向检查 |
| --- | --- | --- |
| 对象需要独立识别、复用、被其它事实引用或拥有自己的生命周期 | Node | 独立性是否真实存在，还是仅因为文本里出现名词？ |
| 两个对象之间有明确的二元事实，其时间、来源、角色属于这个关联 | Relationship 及其 Property | 不把任职日期放成人的永久属性；方向与端点语义要明确 |
| 简单从属值无独立身份/关系需求 | Property，必要时为列表 | 列表元素只是值还是需要引用的实体？重要可查询关系不能藏成逗号字符串 |
| 事实有多名参与者、独立可引用身份、多条证据或独立状态变化 | 事件/任职/论断等中间 Node | 二元关系属性已足够时不要强行实体化；多边结构的完整性也不会自动被端点约束保证 |

关系在 KG OS 是一等图元素，可有自己的 Property，不因需要来源或时间就必然升级为 Node。反之，需要把多条独立证据指向一项论断时，中间对象往往比让证据勉强指向普通关系更清晰。

关系的定义方向用于统一表达，不等于现实因果、授权或唯一连接。反向读取通常不需要再存一条同义反边；确实存两种关系时定义不同含义或明确同步责任。自然语言“属于”不能同时表示组织 membership、类型继承和业务归属。

## 来源与证据

外部资料、引文或可争议论断需要能追溯所依据的材料及位置。轻量场景可以保存来源定位符和版本/采集信息；当来源需要复用、版本管理、独立查询或多重证据时再分出来源对象。来源可以是文档编号、受控资源引用或 URL，不以公网链接可访问作为唯一有效形式。

区分**原始材料、捕获的材料版本、提炼的知识、支持/反驳/仅引用关系**。相同 URL 可能指向不同时刻内容；需要复核当时原文时，必须保留内容或其可核实的持久定位，只有 ID、时间或摘要不足以恢复内容，也不能假设 KG OS 自动归档网页。引用关系不证明其支持该结论，更不证明结论真实。未知作者、发布日期、定位符不要补造；模型要能表达未知并在使用时保留限制。模型具备来源字段不证明实际实例填入了真实来源；后者由实际知识任务核对。

## 时间与生命周期

先问时间约束回答什么问题，再选日期或时间点：发布、生效、失效、事件发生、采集、结果生成和录入分别有不同含义。Commit 时间表示数据库版本生成，不自动等于业务有效时间；一个历史 State 中也可以保存未来生效规则。

需要时间区间时明确边界是否包含、时间精度和时区，以及缺失结束时间代表**未知**还是**确认开放结束**。半开区间 `[start,end)` 是可选约定，不是所有领域默认值。未知时间不能填当前时间或任意午夜；只有日精度不伪装成精确 UTC 时刻。若要求“当时系统知道什么”并且“现实何时有效”，区分记录版本与业务时间，不把一个 `date` 承担两者。

状态字段先定义每个状态意味着什么、需要哪些证据、能否逆转。`approved` 不等于 `implemented`，`planned` 不等于 `occurred`。名称中的状态和描述中的状态转移都不产生数据库自动校验；必要的跨字段/跨对象条件由授权工作流检查。

## 身份、类型、单位与未知

区分 element identity（数据库元素身份）、Definition 的 identifying name、业务唯一键、显示名称。只有业务要求确认唯一范围时才加键；范围可能包括组织、来源、方案或组件。两个同名人物可能不同人，两个不同名字也可能同一人。合并需要身份依据，不靠相似度阈值猜测。

标识符不因只含数字就用数值类型；数量才依据单位/精度选择数值。金额、测量值等模型须表达解释它的币种、单位、尺度、方法或场景，不混加不同单位。精确十进制要求不能被浮点近似默默替代；选当前数据库可表达且满足精度的方案，必要时明确范围/整数最小单位或文本解析责任。

缺失、空字符串、零、假、未知、不适用不等价。只有业务区分它们时增加明确表示；不要给每个可选字段机械增加一套状态。资料来源或关系事实的可信度数值没有校准依据时不自创 `confidence=0.9`。

## Constraint 与 Index 的决策

只根据真实不变量设置 `required`、`unique` 或复合 `key`，而非“看起来重要”。如果对象在合法的早期状态并不知道某字段，不应为方便让它全程必填；可选值不表示永远无需验证。复合唯一不等于每字段分别唯一，唯一性也不等于关系数量约束。

索引按实际过滤、排序、连接或检索需求设置，不自动给所有字段加索引。索引名称必须能定位真实索引且避免现有资源冲突；Domain 不是命名空间。现行 KG OS 中 `unique/key` 自带对应 Range 索引，不要重复声明同 target/同有序字段的 Range 索引。多字段顺序、共享索引全部 targets 是语义，不按美观排序或截断。

全文索引解决文本匹配，托管语义索引解决一个 STRING source 的语义访问；它们不是业务真实性约束。当前 `vector` 是 Index 类型，不是调用方 VECTOR Property；不额外存 raw embedding，不填写 provider 密钥或 per-index 参数。多个 target 不等于多个 source 字段。实际搜索质量和外部 Provider 可用性须另测，不由模型定义成功推出。

## KG OS 表达边界的判断

Domain 只组织定义，不是实例权限、独立数据库、namespace 或继承；允许不使用 Domain 和多重组织。额外 Label 也不自动建立子类推理。把 OWL/RDF 或其它标准概念转为 Property Graph 时，只移植需要的含义，不移植未经实现的推理语义。

Node 和 Relationship Definition 在当前 KG OS profile 都须有非空 `properties`，但实例是否必填由声明决定。确无任何有意义字段的概念暴露的是表达差异：说明限制并评估其它表达，不造必须填的占位字段。`from/to: null` 可表达开放端点，不因为“规范”强制具名端点；当业务本身要求特定端点类型时应按要求约束。

说明文本中的 enum、数值范围、时间先后、图无环、边的数量和跨字段等式，不自动变成可执行 Constraint。不要在公共 YAML 中发明 `enum`、`minimum`、`maxCount`、`check` 或其它未支持字段。必须明确由 Schema、查询检查还是外部工作流保证；无法保证的要求不能宣称已经落地。
