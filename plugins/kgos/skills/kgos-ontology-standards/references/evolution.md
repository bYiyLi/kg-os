# 本体创建、修改与维护

本文件用于宿主任务中关于本体变化的判断；不是独立迁移执行器。具体 Patch 和 SDK 签名由当前 `kgos_docs` 提供。每项检查随变化影响而定，不要求小修文案执行全库扫描、创建分支或额外输出报告。

## 创建与局部扩展

本体 Patch 可能新建 Commit，支持 `message` 时应从当前 `kgos_docs` 的 `guides/evolution.md` 获取统一格式，说明新增模型**并说明提交后的已知整个世界与用途**，不把本次差异充作世界简介；模型写入失败不可写为已成功。按实际返回的 State 回读 Message 和 Ontology，禁止用默认 Branch 当前 Head 代替已提交版本。

新模型应有真实问题和代表性实例；先判断候选旧模型是否语义相同，只有确认缺口才新增或扩展。创建中间对象、共享索引、复杂约束都要指出当前需要；缺乏依据时保留更简单但不丢失需求的方案。

在现有实例中修改，必须基于目标 Branch 的真实 Head 和对应 canonical 定义；概念草案或另一分支的 YAML 不是写入基线。读取局部相关定义、引用、共享资源和实例即可，不要求导出全库。无权读取某项依赖时不宣称无影响。

## 按变化性质分析

| 变化 | 先核对什么 | 允许的判断 / 不允许的捷径 |
| --- | --- | --- |
| 修正描述错字、显示标题 | 含义是否不变 | 可小范围修正；不借机改类型、键、索引或重建数据 |
| 修改概念/字段含义 | 历史实例是否仍被正确解释 | 即使只是 description diff，也可能是语义破坏；必要时建立新概念并显式迁移，不包装成无害文案 |
| 新增可选字段/关系 | 对旧数据与现有查询是否兼容 | 不自动给旧记录造值；关系新类型也有自己的实际字段和语义 |
| 收紧类型、required、unique/key、端点或附加 Label | 受影响实例和所有重叠 Definition 是否满足 | 样本不能证明全范围符合；范围大时先说明分批检查/成本，不在证据不足时宣称可安全应用 |
| 放宽约束 | 下游查询和业务是否依赖原不变量 | 放宽不是必然向后兼容；先找依赖，保留实际授权 |
| 纯改名 | 身份和含义是否保持、目标名是否冲突、引用/值/查询如何跟随 | 采用公开 rename 合同，不用 delete+add 假装无损 rename |
| 改变来源/时间/单位含义 | 已存值是否可按新义解释、原始证据能否转换 | 不能把 capturedAt 改名为 publishedAt、把厘米原数值改名为米就声称迁移完成 |
| 拆分或合并模型 | 身份映射、实例归类、多义值、关系重新连接及无法判定的项 | 先形成有证据的迁移规则；保留未决项，不自动去重、吞并或删除 |
| 删除字段/Definition/Domain/索引 | 仍有的值、实例、Schema/查询依赖、共享目标 | 区分各类删除效果；不以“最近未用”或第一批无结果认定无依赖 |

## 改名、删除与共享资源

纯 Property 改名须使用当前合同的 input-only `renameFrom`；新 canonical read 不保留该标记。顶层 Definition/Domain 使用 Git Rename entry。改名不是改义：当旧语义与新语义不等价，必须提出真正转换方案。保留未变的索引真实名称、配置和字段，不因换名字重新创建一套资源。

现有 Knowledge 的 Label、关系类型或字段迁移由公开 Patch 编排合同处理，但不得推广为“任何模型修改自动修复数据”。多 Label 覆盖、目标字段已存在等会造成冲突；不能全图改写同名字段。关系替换可能改变实际关系 Ref，应使用返回 transition 和新 State 回读，不承诺所有元素 ID 永远不变。

删除 Definition/Property 不隐式删除业务知识；实际还有实例、值或未解决结构依赖时应拒绝或在明确授权的同一目标修改中处理。删除 Domain 只删除组织关系，不删除成员定义或知识。删除索引不删除正文。过去 State 保留过去含义，不能因此跳过当前依赖的兼容检查。

共享 Full-text/Managed Semantic Index 的各 Definition 展示是同一资源，不是多份独立所有权。需要缩小覆盖面时调整完整 `targets`；从一处删除整条共享索引声明会删除全局索引。对 composite/shared 资源的变化核对全部实际受影响者，不能把“移出 Domain”当作移除索引目标。

## 原子性、失败与验证

关联的模型和实例变更需要原子完成时，使用当前公共合同支持的一个混合 Object Patch；不要以多次 mutation 后再合并/回退声称原子。单次 Patch 的成功、后续读取失败和整个 JavaScript 调用失败是不同事实。

遇到过期基线，读取新 Head 比较真实变化后重建最小 Patch；不得盲目重放。写入超时、取消、断线或回执缺失时先核对真实 State/History/目标内容再决定是否继续，不能把未知当未写入。也不能因为读回失败再创建同一批对象。

验证分三层：

1. **结构**：新 State 的 canonical 定义符合目标；无无关字段/索引/引用变化。
2. **数据**：已有对象和值按显式方案保留或转换；约束失败无部分副作用；有代表性边界实例和必要的全范围检查。
3. **使用**：原需求问题仍能得到正确答案，新增需求得到支持；调用方查询/导入所依赖的名字和语义已经处理或明确待迁移。

只做文本方案时只能报告设计审查；未运行查询不可写“验证通过”；基于少量样本只能说明所查样本。影响与验证强度应相称，不能要求每次标题修正都做外部系统迁移。

## 持续维护模型而非改造世界

从实际症状定位模型问题：持续出现多个同义类型、来源不能定位原文、同一字段混用单位/时间角色、关系含义混杂、查询必须反复解析长文本或不可满足旧约束。先区分实例填错、数据不足与模型本身表达不足，避免每次脏数据都修改 Schema。

类型废弃可通过用户选择的说明和迁移策略表达，不发明公共 `deprecated` 字段或内核自动停写开关。合并/拆分/删除需要真实用途和依赖证据；空类型可能是尚未填充的合法模型，冗余候选不是自动删除依据。周期任务安排归外部维护任务，本 Skill 不建立调度或自动写 VLog。
