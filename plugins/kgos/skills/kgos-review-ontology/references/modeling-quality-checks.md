# KG OS 已生效模型质量检查

本文件检查已生效模型的完整定义、语义一致、使用边界和发现入口，不要求取得原设计才可开始。

## 一 读取实际模型

通过 kgos_docs 读取当前版本的以下文档；沿方法文档读取实际调用所需请求及返回类型，不根据示例猜测字段。

| 检查动作 | 文档路径 |
| --- | --- |
| 固定版本与读取定义目录 | guides/reading.md、sdk/evolution/get.md、sdk/ontology/read.md |
| 理解定义结构并取得完整原文 | guides/ontology.md、guides/objects.md、sdk/object/readText.md |
| 核对相关知识与实际查询 | guides/graph.md、sdk/graph/query.md |
| 发生读取错误 | guides/errors.md |
| 需要比较历史变化且历史在允许范围内 | guides/evolution.md、sdk/evolution/diff.md |

使用 kgos_query 执行 evolution.get、ontology.read、object.readText 和需要的 graph.query；每次读取使用已固定的对应分支 State。只调用本次检查需要的方法。

ontology.read 用于发现 Domain 和定义入口、检查预览是否易于理解；完整配置由 object.readText 读取 canonical YAML 核对。摘要可能省略内嵌约束，不能从摘要缺失推断字段不存在。未读完的分页、截断原文、访问失败均记录为覆盖缺口。

kgos_ontology_overview 读取当前连接全部分支，仅在全部分支读取获准时使用。它不接收 at；固定 viewRevision 完成分页，并核对各目标 Head 与审核 State。视图过期或 Head 不同，不把预览内容与原 State 拼接。单分支范围用定向 ontology.read，不能先读取全分支再过滤。

## 二 节点与概念

检查定义是否说明实际代表的对象、纳入与排除边界、与相邻概念的区别。用已有实例或标明为构造的例子，检查同一对象是否能被稳定识别；变化、阶段与角色是否被误当成新对象。

检查类型与实例是否混淆。上下位关系的下位实例应满足上位定义；按主题归类、Domain 层级、包含组成或业务关联不能直接当作继承。平台未证实执行继承时，说明性上下位不能被报告为已实现推理。

允许参考本体以不同方式表达现实。只有已采用的语义承诺、领域要求或具体矛盾支持时，才判定违反要求；“不像 BFO”或“没有某个顶层概念”不是独立缺陷。

## 三 关系

读取端点定义并核对 from、to、方向、角色和成立条件是否相符。检查二元关系的正例、反例、数量与有效时间；涉及多方事项时，检查现有节点和二元关系是否保留参与者及同一事项的关联条件，不因多方场景本身判错。

检查关系属性是否描述该关系，而非错误归属端点；与节点约束组合后是否矛盾。名称相同不证明关系含义相同，反向读法不证明关系对称。

## 四 属性和约束

核对属性的语义、归属、类型、值域、单位、数量、时间、缺失和未知值处理；仅检查场景实际需要的限制，不把本清单所有项目变成每个属性的强制字段。

比较原生配置与可读说明：同一限制是否一致，必填、唯一和索引是否有适用依据。身份判定不能未经依据压成唯一键；索引存在不等于已证明查询有效。

区分平台自动校验的原生约束与需要使用者检查的说明性约束。只有当前接口合同或实际证据支持，才声称某约束会被执行。文字里出现“必须”不证明平台会拒绝违规数据。

## 五 定义是否足以指导知识使用

只依据已保存的定义，检查能否判断：
- 哪些知识属于该节点，哪些不属于。
- 同一对象如何识别，属性如何填写，何时缺失或未知。
- 哪些关系可建立，需要什么依据，哪些情况下不成立。
- 正例与反例是否符合定义，示例是否被误写成事实。

不要求所有定义都套同样长度和格式。说明不足须指出具体无法判断的写入场景，不因没有某个标题就判定模型错误。

目标全文、原始图布局和设计自检可以保存于独立设计记录，不要求重复放入运行定义。但影响实际知识使用的边界、身份和条件不能仅靠未加载的聊天或设计稿才能获知。

## 六 结构与入口

检查 Domain 的组织语义、定义归属及发现路径是否清楚；Domain 不等于继承、实例主题树、权限或命名空间。仅在实际造成歧义、遗漏或不可发现时记录问题，不为分类偏好制造问题。

从获准范围的 Domain 或定义入口查找相关模型，核对是否能取得完整说明。依据端点和方向重建的结构图不等于原图布局；图上没有保存的解释也不能假定可恢复。

## 七 真实知识和场景

读取与已发现语义风险相关的实际知识和关系，记录抽样范围。数据违反清楚的定义，不自动证明本体定义错误；定义允许互相矛盾的知识，才进一步核对是否为建模缺陷。

对用户用途中的典型问题，将预期来源与实际结果分开记录。实际查询使用当前获准接口；查询成功但返回空集，只证明该查询执行及该次返回结果，不证明召回或模型覆盖正确。

没有真实数据时仍可检查定义内部一致性和构造场景，但将实际数据适用性、查询召回和真实使用效果列为未验证。

## 八 结论与证据边界

每项判断区分：
- 已发现问题：实际定义及适用依据支持具体矛盾、遗漏或不合理后果。
- 未发现问题：在已检查范围和依据下未发现缺陷。
- 无法确认：缺少定义、资料、业务预期或验证条件。
- 不适用：该检查不属于当前模型的实际场景，说明原因。

原设计与落地定义一致，不证明原设计语义合理；当前模型语义合理，也不证明历史转换完全无损。本审核以当前实际模型为对象。读取历史设计仅用于理解已有语义承诺，不把前一技能的自检结果直接沿用为本次结论。

影响尚未观察到时使用“可能导致”并说明触发场景，不把推演写成已发生。
