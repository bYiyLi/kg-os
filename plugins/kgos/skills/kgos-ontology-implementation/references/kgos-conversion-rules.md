# KG OS 本体转换规则

## 1. 使用随包规则并加载实时合同

在已确认的实例中调用 kgos_docs，读取索引及 serverInfo.version。已有同连接、同版本的完整文档可以复用；按当前操作加载：

| 操作 | kgos_docs 路径 |
| --- | --- |
| 固定分支、读取 Domain 与定义 | guides/reading.md、sdk/evolution/get.md、sdk/ontology/read.md |
| 定义映射与完整原文 | guides/ontology.md、guides/objects.md、sdk/object/readText.md |
| 提交本体变更 | sdk/ontology/patch.md、sdk/types/PatchRequest.md、sdk/types/PatchResult.md、guides/errors.md |
| 涉及知识对象或 vlog 写入 | sdk/object/patch.md；涉及查询时加 guides/graph.md、sdk/graph/query.md |
| 比较实际改动 | guides/evolution.md、sdk/evolution/diff.md；沿方法页读取实际使用的请求及返回类型 |

本文件是本 Skill 随包提供的转换、定义说明、验收和 vlog 记录规范；输入格式使用 assets/ontology-definition.md。按 SKILL.md 的流程加载相应章节，不依赖另一个同名或旧版规范 Skill 才能理解本流程。

这些随包规则不能替代当前服务的字段和接口合同，也不构成写入授权。遵守用户的当前范围、宿主权限和工具确认要求；规则与实际接口不兼容或必需资源不可读时，停止依赖它的操作并指出缺口，不自行安装资源、换实例或调整权限。

## 2. 固定基准与建立对应表

通过 kgos_query 调用 evolution.get({state: "branch/" + branch})，取得获准目标分支的不可变 State。后续 ontology.read、object.readText 及需要的 graph.query 均使用该 State，并按接口要求读完相关分页。

读取已有 Domain、节点与关系定义，以及受影响的知识和依赖；修改对象必须读取完整 canonical YAML。按语义和身份判断复用，不能只凭同名合并。Domain 用于组织定义，不等于类继承、实例归属、权限或命名空间。

逐项拆解输入模板，建立下表。条目用原材料章节及名称定位；写入前填现有 Ref 或本次临时 alias，写入后替换为服务端返回的正式 Ref。

| 原设计条目 | 原意及适用范围 | 目标分支、对象、字段 | 表达方式 | 回读位置与核对结果 |
| --- | --- | --- | --- | --- |
| 实际章节与条目 | 需保持的含义、条件与限制 | 明确到 Ref 和字段路径 | 原生配置／说明性规则／原文保留 | State、Ref、字段及通过／未通过／未验证 |

一个条目需要多处共同表达时列全，不能用“已放入 description”概括全部映射。按以下两类标明保存去向：
- 本体定义：节点、关系、属性、约束，以及正确理解和使用它们所需的释义、边界、身份、条件、正反例和参考映射。
- vlog 完整设计记录：原设计全文，包括目标与边界、原始图、变更说明、参考依据、场景验证与设计自检，并另附本次实际转换和验收结果。

完整设计记录不要求在本体定义中再保存一份。目标、图注或场景中若含有影响知识写入的语义条件，仍需提炼到相关定义中；不能以“全文在 vlog”作为省略必要约束的理由。vlog 尚未保存时标记未完成，不把记录计划填成已保存位置。

## 3. 将设计落实到定义

以当前公共接口合同和实际对象确认字段，不向未知字段写入自造结构。节点类型对应 Node Definition，关系类型对应 Relationship Definition；Property、Constraint 和 Index 是所属定义的内嵌结构，不另建知识节点表示类型。

### 节点定义

- name 保存已批准类型名称；description 保存概念定义、纳入与排除边界、身份判定、上级概念、参考本体映射及适用约束。
- 在 description 中明确“可保存的知识”“不应保存的知识”“写入时如何判断”，依据来自原设计的边界、身份与约束。后续 AI 不应靠本次聊天才能理解这些要求。
- 保存原设计正例和反例，并说明为什么属于或不属于；示例仅用于解释，不作为真实知识实例写入。
- properties 保存属性定义；平台能够准确表达的约束写入对应 constraints 或属性原生配置，不能只写在描述中。

### 关系定义

- name、from、to 保存关系名称与端点定义。description 用“（起点类型及角色）—关系→（终点类型及角色）”说明二元关系，保留方向、成立条件、数量、时间及共同约束。
- 写清什么时候可以建立关系、需要何种依据、什么情况不应建立；保存成立与不成立的例子及原因。
- 多方事项沿用原设计的节点与多条二元关系，保留它们指向同一事项的条件；不得为了适配端点擅自删参与者或重新设计。
- 关系属性仍归该关系的 properties，不挪到端点而改变语义。

### 属性定义

- 在所属节点或关系的 properties 中保留 name、type，以及当前合同支持且与原意相同的 required、constraints、indexes 等配置。
- 属性 description 写明含义、值的使用方式及原设计涉及的单位、范围、数量、时间、缺失或未知值处理；需要跨属性判断的规则在所属定义 description 中表达，并明确涉及哪些属性。
- 用合法值与容易误填的值解释关键限制。原设计未规定的业务规则不能由例子推导为新增限制；缺少会改变含义的处理规则时回到用户确认。
- 不因字段存在而自动添加必填、唯一、索引或默认值，也不把“未知”擅自转换为零、空字符串或某个状态。

### 原生配置与说明性规则

准确可执行的原生配置优先使用，description 同时给出可读含义，便于预览理解。原生配置与说明必须一致。

平台没有已证实的原生能力，但可以完整保留语义时，将规则明确标为“说明性约束，写入与使用时检查；非平台自动执行”。如果原设计要求平台强制执行，说明性保存不构成等价转换，必须确认替代方案后再写入。

身份、上下位、时间、基数或推理能力，不能因使用了相同名称就宣称已实现。不得把领域导航当继承，也不得把业务语义压成无依据的唯一键。

定义内容可按上述信息组织简短段落，不要求所有对象套用相同长文。补充使用指导必须能追溯到原设计；新构造的例子标为示例，不虚构事实或来源。

## 4. 定义发现与关系图

通过目标分支的 Domain 和定义入口，使后续 AI 能找到节点、关系、属性及其完整说明。Domain 按已有组织语义归入定义，不为存放目标、原图或自检创建额外 Domain、类型或字段。

本体定义不重复承载完整设计稿。依据已保存的节点和关系端点、方向与名称，可以重新生成当前结构的关系图；原图布局、视觉分组、标注、删除项及未保存的解释不能仅靠结构恢复。需要查看原图和设计过程时，读取第 7 节保存的完整设计记录。

原图表达的继承、基数、时间或跨定义条件如果属于本体语义，必须在对应定义中保留，不能只留下图线。重建关系图时区分原生关系、说明性上下位和其他标注，不将所有线条都解释成知识关系。

定义说明的长度和读取完整性仍按实际合同及回读验证；遇到截断或不支持的字段时停止相关写入或验收，不以全文归档替代缺失的运行定义。

## 5. 提交与恢复

对应表完整、依赖具备且变更仍在授权范围内后，使用 kgos_mutate 中的 ontology.patch；确需知识对象时使用 object.patch。按当前合同由同一基准 State 的 canonical YAML 生成精确 Git Extended Diff，不使用 JSON Merge Patch。新建用请求内 alias，成功后读取 created；重命名遵守合同并保存 transitions。

提交前核对实际增删改及依赖；内容已经一致时不提交空变更。记录每次成功返回的不可变 State。单次 Patch 的原子性不扩展为多次调用的事务，后续失败不代表先前写入回滚。

- 基线过期：重新解析同一目标分支并回读受影响对象，复核并发变更后重建补丁。
- 原文不匹配：回读指定 State 的完整 canonical YAML，重建精确差异。
- 超时、断线或结果不明：先查实际目标分支 State、历史及对象，确认哪些已生效；不重放已完成部分。仍未知则停止可能重复或破坏数据的动作。
- 权限拒绝或超出批准范围：停止对应操作，不切换环境绕过。

## 6. 双向一致性验收

固定本次最后成功变更的不可变 State 作为验收 State；无需变更时使用已核实的当前 State。各项证据必须标注 State，不能混用移动分支的后续内容。

### 完整定义验证

通过 kgos_query 在验收 State 调用 object.read 或 object.readText，逐项检查完整定义及内嵌属性、约束、索引。ontology.read 和全分支预览用于发现和可读性检查，不能替代完整原文。

例如，某属性的 key 约束可能存在于 canonical YAML，但不出现在 ontology.read 的属性摘要中；即使预览显示名称和类型正确，仍须核对该内嵌约束。不得根据摘要缺失推定原生配置不存在或验收通过。

### 双向比对与使用检查

1. 原设计 → 本体定义：对应表中归入本体定义的各项均有实际位置，含义、边界、端点角色、方向、类型、数量、时间、强制程度、正反例及必要依据未丢失。完整设计归档另按第 7 节验收，不要求在定义中重复存放目标、原图和自检。
2. KG OS → 原设计：每个本次新增或修改的配置和说明均能追溯到原设计、批准的适配或不改变语义的使用指导；排查擅加约束、扩大适用范围与示例变事实。
3. 只依据已保存内容，用原设计正例、反例及典型问题判断可以保存哪些知识、如何填属性、何时建立关系，并逐项对照原设计预期。不能从模型反推预期，也不为了验收擅自写入示例数据。
4. 通过 evolution.diff 比较固定的写入前后 State，核对实际变化与批准清单，读取受影响依赖确认保留内容未误改。原设计检查结果、文本推演、实际只读查询和写入测试分别报告；空查询不证明召回正确。

### 发现入口与预览验证

从目标分支的 Domain 或定义入口开始，不借助当前聊天中的对象列表，确认能够找到完整定义详情，并检查说明是否提供必要的使用边界和读取定位。

优先用 ontology.read({at: 验收State, ...}) 完成定向预览及分页。只有获准读取全部分支时才调用 kgos_ontology_overview：新建视图后先核对目标分支 Head 等于验收 State，再用同一个 viewRevision 读取相关全部窗口。该工具没有 at 参数，不能让它读取任意指定历史 State。

若预览中 Head 已变化或 viewRevision 过期，不将其与原验收证据拼接。过期后重新取视图并核对 Head；并发推进时保留原 State 的定向回读结果，将当前全分支预览标为尚未同状态验证，必要时经重新评估后验收最新 State。限定单分支的任务不得调用全分支预览再过滤。

每项结果记录“通过／未通过／未验证／不适用”及依据。信息遗漏、失真或入口不可用不得通过；不适用说明原因。仅在批准范围内修正，修正后针对新的验收 State 重查受影响定义、依赖、对应表和入口。未完成项不能被“写入成功”覆盖。

## 7. 完整设计与工作记录保存到 vlog

### 确认现有模型是否能承载

此节为本 Skill 自带的记录规则。执行时先核对日志写入授权，通过 kgos_query 固定 vlog 自身的 State，读取实际 Domain、相关定义的完整原文和代表性记录，确定可用类型、字段、关系及发现路径。

检查现有字段的语义是否适合保存本次完整设计正文，当前合同是否规定容量，全文能否完整读取，记录能否通过本体名称、源分支、设计版本或实际目标引用查到。存在 STRING 字段或短文本样例不等于已证明长文可保存。

若无法确认承载能力，列出缺少的字段合同、容量依据或实际验证条件，停止相关日志写入。需要验证写入、修改 vlog 模型或增加保存范围时，提出具体方案并获得对应授权，不擅自改模型、将文档塞入摘要字段或以外部链接代替全文归档。

### 保存内容

在已核实的现有模型内保存：
- 用户确认的完整本体设计，保持输入模板的全部内容，包括原始关系图与设计自检。
- 实际目标实例、分支、设计来源或版本、源名称与实际 Ref 的对应，以及真实增删改。
- 写入前后 State、定义验收 State、检查结果与证据范围、未通过或未验证项、恢复及部分完成情况。

保留“原设计自检”和“本次落地验收”两个不同结果，不把原设计通过当作本次运行通过。完整设计可作为实际落地事件的记录材料，但尚未发生的工作不能写成已发生；无模型变更时如实记录核验及无需变更的结果，不虚构变更事件。

引用其他分支对象时使用实际支持的定位字段，不假定能够建立跨分支图关系。记录已有则核对同一实际工作及版本，避免重试产生重复事件。

### 回读验收

日志提交成功后固定其返回 State，回读完整正文、关联和定位字段，逐节比对原设计全文，核对关系图文本、设计自检、实际变更和本次验收结果均完整且无失真；再从实际检索入口验证能够找回该记录。

字段容量、全文回读或检索任何一项未验证，均不得宣称完整设计已无损保存。日志失败或结果不明按第 5 节核实，不重复记账。分别报告“本体定义写入”“定义验收”“完整设计归档”；日志未完成不推翻已确认的定义结果，也不视为整个流程已完成。
