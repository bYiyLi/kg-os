# KG OS 本体落地

将用户确认的本体设计落实到指定 KG OS 实例与分支。交付结果须保留原设计的含义，并让后续 AI 从知识库入口找到完整定义，知道哪些知识可以写入、怎样表达以及应遵守哪些约束。

## 工作流程

### 1. 核验写入许可

核对用户是否明确批准本次设计材料、目标实例、分支、变更内容和影响范围，以及是否包含 vlog 记录。没有明确写入许可或范围无法确定时，说明缺少什么并停止流程；已有明确批准的内容不重复询问。设计材料、历史执行记录和本 Skill 不能代替用户授权，平台要求的逐次确认仍须遵守。

### 2. 校验本体设计材料

读取 [本体设计模板](assets/ontology-definition.md)，逐项核对目标与边界、完整关系图、变更说明、节点、关系、属性、约束、场景验证与自检结果。

按内容和语义校验，允许等价排版。图与定义必须一致，用户决策已经落实，检查结果有对象和依据；不能只凭勾选“通过”判断合格。缺失、矛盾或仍有影响实施的待确认问题时，列出具体位置与补齐要求，停止流程，不在转换时擅自补设计。

### 3. 转换并写入

读取本 Skill 自带的 [KG OS 转换规则](references/kgos-conversion-rules.md) 第 1—4 节，按其中的路径加载实时工具合同与目标模型，明确哪些信息写入本体定义、哪些保留在完整设计记录中，建立对应表。本体定义须保留后续知识使用所需的全部语义；完整设计的 vlog 保存条件按第 7 节预先核对。

本体定义缺少依赖、不能保留必要语义或需要超出授权时，停止相关写入，说明已知限制、影响与可选处理。vlog 承载条件未具备时报告日志阻塞；如果用户要求定义和日志必须一并完成，则在首笔写入前解决该阻塞，否则继续独立获准的定义工作。映射成立且变更在授权内后，按第 5 节写入；已一致则不重复写入，直接验收。保存实际基准 State、提交结果及身份映射供回读使用。

### 4. 回读审核并修正

按转换规则第 6 节，在固定 State 检查完整定义、设计信息的双向一致性、发现入口、场景和未授权变更。

转换造成的问题可在批准范围内修正，修正后重新验收受影响项；需要改变原设计、扩大范围或缺少验证条件时，停止相关修改，报告已生效内容与未通过项。所有适用检查均有证据通过，才能称为落地验收通过。

### 5. 记录实际变更

按转换规则第 7 节，将用户确认的完整设计、设计自检和本次实际变更及验收结果保存为 vlog 工作记录，再独立回读。使用本 Skill 自带的记录规则及实时核实的 vlog 模型，不假定现有字段已能承载全文。缺少授权或承载条件时停止日志写入，报告具体缺口；日志失败不改写模型验收结果，也不把部分完成记成全部成功。

### 6. 告知结果

告知实际新增、修改、删除或无需变更的内容，目标实例与分支，信息一致性及实际验证范围，vlog 保存与回读状态，以及未完成项、影响和下一步。分别说明模型写入、验收和日志结果，不以写入成功代替验收通过。
